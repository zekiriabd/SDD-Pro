# Spec: reseau-assistantes

FEAT ID: 19-Spec-Reseau-Assistantes
Spec ID: spec-reseau-assistantes
Status: Draft

> **Pré-requis schéma** : la table `dbo.Employee` est supposée préexistante en base (cf. `spec-connexion` FEAT 1, `spec-inscription` FEAT 3) avec **au minimum** les colonnes suivantes consommées par cette FEAT : `EmployeeId INT NOT NULL` (clé primaire identité), `Nom NVARCHAR(25) NOT NULL`, `Prenom NVARCHAR(25) NOT NULL`, `CodePostal NVARCHAR(10) NULL`, `Ville NVARCHAR(50) NULL`, `Telephone NVARCHAR(...) NOT NULL`, `Disponible BIT NOT NULL DEFAULT 0`. La colonne `Disponible` est supposée préexistante en base (gérée par `spec-mes-donnees` FEAT 18 ou par flux administratif équivalent — hors scope ici) ; toute incohérence schéma → STOP DBA avant `dev-backend`. Source de vérité = DB existante (cf. `docs/principles/source-first.md`). Aucune migration DDL n'est introduite par cette FEAT — la table est lue uniquement, jamais écrite.

## Context

L'application Demo expose aujourd'hui dans son menu principal latéral (cf. `spec-menu-principale` FEAT 5) un item « **Mes contrats** » qui pointait initialement vers une page de gestion des contrats employeur/famille. **Cet item est inadéquat dans le modèle métier actuel** : la souscription d'un contrat est déjà couverte par `/contrats/nouveau` (cf. `spec-souscrire-contrat` FEAT 6, déclenché depuis `/bebes`) ; aucune page `/contrats` (liste des contrats) n'est implémentée — l'item est un libellé orphelin pointant vers une route morte. Par ailleurs, **un besoin métier nouveau émerge** : une assistante maternelle connectée souhaite consulter le **carnet de contacts professionnel** des consœurs disponibles dans sa zone géographique afin de pouvoir les joindre (téléphone, SMS) en cas de surcharge ponctuelle, remplacement de congés, recommandation auprès d'un parent, ou échange informel sur la pratique. L'application **ne gère pas la communication** elle-même (pas de SMS in-app, pas de chat, pas de notifications push) — elle expose **uniquement** le numéro de téléphone, à charge de l'employée d'utiliser le composer natif iOS / Android pour appeler ou envoyer un SMS hors application.

Cette spec **étend `spec-menu-principale` (FEAT 5)** par deux opérations atomiques :
1. **Renomme** l'item de menu « Mes contrats » en « **Mes Contacts** » (libellé visible utilisateur) et la route SPA cible `/contrats` en `/contacts` (URL canonique). L'icône de l'item passe d'un glyphe « document/contrat » à un glyphe « carnet de contacts / personnes » cohérent avec la nouvelle sémantique (SVG inliné, 23×23 px, color tokens `var(--nj-ink-700)` au repos, `var(--nj-coral-600)` actif — héritage FEAT 5).
2. **Introduit** une nouvelle page SPA `/contacts` qui rend la **liste des assistantes maternelles disponibles** lues depuis la table `dbo.Employee` (filtre `Disponible = 1`), avec deux modes de filtrage géographique au choix de l'utilisatrice : (a) « **Ma ville** » (filtre additionnel par `CodePostal == session.Employee.CodePostal`) — mode par défaut à l'ouverture de l'écran, (b) « **Tout** » (aucun filtre géographique — toutes les employées disponibles tous codes postaux confondus).

> **Note rename** : aucun fichier de page nommé `Contrats*.{razor,tsx,vue}` n'existe dans `workspace/output/src/{AppName}/` à la date de cette FEAT (vérifié par `Glob "**/contrats/*"` et `Grep "/contrats[^/]"`) ; le rename consiste donc uniquement à (a) modifier le libellé `"Mes contrats"` → `"Mes Contacts"` dans le composant menu, (b) modifier la cible de navigation `/contrats` → `/contacts`, (c) remplacer le SVG d'icône. **Si** un agent constate au moment de l'implémentation l'existence d'un composant `Contrats*` ou d'une route `/contrats` enregistrée (héritage non documenté), il **supprime** le composant et la route en même temps que le rename (cf. AC-1, AC-2). Aucune migration de données n'est requise (la table `Contrat` reste inchangée — c'est seulement l'item menu UI qui change de sémantique).

Le mockup `workspace/input/ui/19-1-Spec-Reseau-Assistantes.html` matérialise le rendu canonique de la nouvelle page `/contacts` : barre supérieure (hamburger + logo `Nounou<em>Job</em>` — héritage FEAT 5), **toolbar** sticky avec (a) **champ de recherche pleine largeur** (pill, icône loupe à gauche, bouton croix à droite quand non vide) et (b) **segmented toggle** « Ma ville » / « Tout » (deux pills, l'actif en background `var(--nj-ink-900)` color `#fff`, l'inactif transparent color `var(--nj-ink-500)`), une **liste verticale épurée** de rangées `.row` (pas de cards, pas d'avatars, pas de boutons d'action — purement informatif : `Prénom Nom · Ville · CP · Téléphone`), un **état vide** (`Aucun résultat. Modifiez votre recherche ou changez de filtre.`), et la tab bar applicative inchangée (item « Réseau » actif). Chaque rangée affiche : (a) à gauche, le bloc identitaire (`Prénom` en weight 700, `Nom` en uppercase weight 700, sous-ligne `Ville · CodePostal` en `var(--nj-ink-500)`), (b) à droite, le **téléphone** rendu en font mono (`var(--nj-font-mono)`, 14 px, weight 500). Aucun bouton, aucune icône d'action, aucun chevron — la rangée n'est **pas cliquable** dans le rendu canonique (consultation pure ; l'utilisatrice copie/note le numéro et appelle hors-app).

> **Note maquette** : la maquette inline une simulation JavaScript (`NOUNOUS` hardcoded + `ME = { ville, cp }`) à des fins d'aperçu visuel uniquement. **Le rendu canonique de cette FEAT** remplace ces données simulées par un appel API réel `GET /api/reseau-assistantes?scope={ville|tout}` (cf. SFD-5) et lit le `CodePostal` de l'employée connectée depuis la session applicative (cf. BR-3) — aucun port de la logique JavaScript de la maquette dans le code de production. La maquette reste la référence pour le **layout, la palette, le segmented toggle et le champ recherche**.

La **stratégie de cache mémoire** (load-bearing pour la performance et l'expérience utilisateur sur mobile bas débit) est la suivante :
- À l'**ouverture** de la page `/contacts`, le frontend déclenche **automatiquement** un seul appel API `GET /api/reseau-assistantes?scope=ville` qui retourne la liste filtrée par code postal de l'employée connectée — le résultat est stocké dans un state local React (ou équivalent stack) sous la clé `cacheVille`.
- À l'**activation** du toggle « Tout » par l'utilisatrice (premier clic), le frontend déclenche **un seul** appel API `GET /api/reseau-assistantes?scope=tout` qui retourne la liste complète des assistantes disponibles tous codes postaux confondus — le résultat est stocké dans le state local sous la clé `cacheTout`.
- À **tout basculement ultérieur** entre les deux modes (« Ma ville » ↔ « Tout ») **tant que la page reste montée**, **aucun appel réseau** n'est émis : le frontend lit directement la collection cachée correspondante (`cacheVille` ou `cacheTout`).
- Au **démontage** du composant (navigation vers une autre route SPA, déconnexion, fermeture de l'app), **toutes les variables mémoire** (`cacheVille`, `cacheTout`, `searchQuery`, `activeScope`) sont **libérées** — aucune persistance en `localStorage`, `sessionStorage`, IndexedDB, cookies, ou cache HTTP applicatif côté client (cf. BR-13). Le but explicite : **ne pas consommer la mémoire du téléphone** au-delà de la durée de consultation effective.
- Au **remontage** ultérieur de la page (l'utilisatrice navigue ailleurs puis revient sur `/contacts`), le cycle reprend à zéro : un appel `GET /api/reseau-assistantes?scope=ville` est de nouveau déclenché par défaut (cf. AC-7).

La **barre de recherche** filtre **en mémoire pure** la collection courante (selon l'`activeScope`) — **aucun appel réseau n'est émis à la frappe**. L'algorithme (cf. SFD-11) normalise la chaîne tapée (`lowercase + NFD + strip diacritiques`) et la cherche en `substring` dans la concaténation des champs `prenom`, `nom`, `ville`, `codePostal`, `telephone` de chaque ligne de la collection cachée. Le filtre est appliqué **après** la sélection du scope (le toggle pré-réduit le jeu de données ; la recherche affine au sein de ce sous-ensemble), et il est **réinitialisé** à chaque bascule de scope (cf. AC-11).

L'écran est une **consultation pure** : aucune action de mutation, aucun bouton appeler/SMS in-app (cf. BR-15), aucune notification, aucun historique côté serveur des consultations (cf. NFC compliance). L'utilisatrice lit le numéro et utilise le composer natif iOS / Android hors application pour joindre la consœur.

## Objective

L'employée connectée ouvre le menu principal → clique sur le nouvel item « **Mes Contacts** » → la SPA navigue vers `/contacts` (la route legacy `/contrats` n'existe plus côté UI ; toute tentative d'accès direct par URL retourne 404 SPA ou redirige vers `/menu`, cf. AC-2). Au montage, le frontend envoie **un seul** appel `GET /api/reseau-assistantes?scope=ville` qui retourne le tableau JSON des employées disponibles partageant le même code postal que la session connectée, sérialisé `[ { employeeId, prenom, nom, codePostal, ville, telephone }, ... ]`. Le frontend stocke ce résultat dans la variable mémoire `cacheVille`, l'affiche en liste épurée, et active la pill « Ma ville » du segmented toggle par défaut. L'utilisatrice peut alors : (a) **basculer sur « Tout »** → le frontend détecte que `cacheTout` est encore vide, déclenche **un seul** `GET /api/reseau-assistantes?scope=tout`, stocke le résultat dans `cacheTout`, et rend la liste complète ; les bascules ultérieures « Ma ville » ↔ « Tout » consomment les caches sans appel réseau ; (b) **taper dans le champ recherche** → le frontend filtre **en mémoire** la collection active (`cacheVille` ou `cacheTout` selon le scope) par match `substring` normalisé sur `prenom + nom + ville + codePostal + telephone` ; (c) **vider la recherche** (bouton croix) → la liste complète du scope actif est restaurée ; (d) **revenir au menu** via le bouton hamburger → la page est démontée, les variables mémoire sont libérées. L'application **n'expose aucun bouton d'appel ou de SMS** : l'utilisatrice lit le numéro affiché en font mono et l'utilise hors-app.

## Quantified Goal (v7.0.0 — anti-GIGO)

- Metric: temps de chargement de la liste initiale (1 requête SQL `SELECT` paramétrée avec WHERE simple) + temps de rendu du tableau côté frontend (calcul pur, pas de fetch additionnel) + latence de bascule toggle (lecture cache mémoire, 0 ms réseau) + latence de filtrage à la frappe (calcul in-memory)
- Target: p95 chargement `GET /api/reseau-assistantes?scope=ville` < 350 ms sur 4G simulé (1 SELECT sur table `Employee` indexée sur `CodePostal` et `Disponible`, payload < 12 KB JSON pour 100 employées) ; p95 chargement `GET /api/reseau-assistantes?scope=tout` < 550 ms (même requête sans WHERE sur `CodePostal`, payload < 80 KB pour 600 employées disponibles à l'échelle du déploiement) ; p95 rendu initial de la liste après réception du payload < 80 ms côté frontend ; p95 bascule toggle Ma ville ↔ Tout après que les deux caches sont peuplés < 50 ms (lecture state React + re-render — **aucun fetch**) ; p95 latence de filtrage à chaque frappe < 16 ms (1 frame à 60 FPS — calcul pur in-memory sur ≤ 600 entrées normalisées une seule fois au chargement)
- Deadline: livraison stack `kotlin-spring-boot × react × shadcn` au 2026-10-15

## Non-Functional Constraints (v7.0.0)

- Expected volume: ~50-150 lignes typiques pour `scope=ville` (densité urbaine moyenne d'assistantes maternelles par commune en Île-de-France) ; ~400-800 lignes pour `scope=tout` à l'échelle du déploiement actuel (toutes communes confondues) ; ~2-5 chargements `/contacts` / employée / semaine (consultation occasionnelle, pas usage quotidien) ; ~0 écriture déclenchée par cette FEAT (la table `Employee` est lue uniquement, jamais mutée) ; total trafic ajouté par cette FEAT < 200 KB/employée/semaine
- Performance SLA: p95 chargement < 350 ms (ville) / 550 ms (tout) (cf. Quantified Goal) ; aucun risque N+1 (1 SELECT plat sans JOIN dans les deux scopes) ; latence de filtrage frontend < 16 ms par frappe (boucle JS `Array.filter` + `String.includes` sur ≤ 600 entrées normalisées une seule fois et mémorisées) ; bascule toggle < 50 ms (re-render React sans fetch quand le cache est peuplé)
- Data retention: aucune nouvelle ligne créée par cette FEAT (lecture seule sur `dbo.Employee`) ; aucune migration DDL ; **aucun cache backend** (la requête est suffisamment rapide pour un appel direct DB à chaque GET — pas de cache Redis, pas de cache applicatif in-process) ; **aucune persistance client** des caches mémoire (cf. BR-13) — libération au démontage
- Compliance: RGPD — le payload expose `Prenom`, `Nom`, `Ville`, `CodePostal`, `Telephone` d'employées tierces ; cet **annuaire professionnel partagé** est légitime par finalité métier (mise en relation entre assistantes maternelles d'un même secteur) et conditionné par le consentement implicite à figurer dans le réseau via le champ `Disponible = 1` (l'employée qui ne souhaite pas être contactée bascule `Disponible = 0` via la page `Mes données` couverte par FEAT 18 — out of scope ici) ; aucun email, aucune adresse postale précise (rue), aucune donnée sensible (santé, religion) n'est exposée par cette FEAT ; aucun log d'accès par employée consultante n'est introduit (consultation anonyme côté serveur — cf. BR-14)
- Integration: nouvelle route SPA `/contacts` + nouvel endpoint backend `GET /api/reseau-assistantes` ; rename du libellé et de la route cible de l'item menu « Mes contrats » → « Mes Contacts » (extension FEAT 5) ; aucune dépendance externe ; aucun service tiers ; aucune notification ; aucun WebSocket / SSE ; **aucune intégration composer SMS / téléphone in-app** (le numéro est texte pur ; l'utilisatrice utilise le composer natif OS hors application — cf. BR-15)
- Degraded mode: si la requête SQL échoue (5xx, timeout), la page affiche un message d'erreur générique `Impossible de charger la liste. <button>Réessayer</button>` qui re-déclenche le GET avec le `scope` courant (cf. SFD-15) ; si la table `dbo.Employee` ne retourne aucune ligne pour `scope=ville` (employée connectée habite dans un code postal isolé sans collègue disponible), la page affiche l'état vide `Aucune assistante maternelle disponible dans votre ville. Essayez « Tout ».` (cf. AC-12) ; si `scope=tout` retourne `[]` (aucune employée disponible dans toute la base), affiche `Aucune assistante maternelle disponible.` (cf. AC-12) ; si la colonne `Employee.CodePostal` de l'employée connectée est `NULL` ou vide (compte non finalisé, cas pathologique), le backend retourne `[]` pour `scope=ville` avec log WARN structuré ; le frontend rend l'état vide `Aucune assistante maternelle disponible dans votre ville. Essayez « Tout ».` et l'utilisatrice peut basculer sur « Tout » qui fonctionnera normalement (cf. BR-9) ; aucun fallback offline / cache local persistant

## Actors

- Employée connectée : assistante maternelle authentifiée, identifiée par son `EmployeeId` issu de la variable singleton de session (cf. `spec-connexion` FEAT 1). Seule autorisée à consulter la page `/contacts` (la route est protégée par le même middleware d'authentification que les autres pages applicatives — cf. BR-1). **Note importante** : le contenu retourné par `GET /api/reseau-assistantes` est **un annuaire partagé** — toutes les employées authentifiées voient (pour un scope donné) le même tableau JSON, à l'exception de leur propre fiche qui est **toujours exclue** du résultat (`WHERE EmployeeId != session.EmployeeId`, cf. BR-7). Aucun filtrage par contrat / par tenant / par établissement n'est appliqué — c'est un réseau professionnel ouvert entre toutes les utilisatrices de Demo.

### Endpoint backend — `GET /api/reseau-assistantes`

- SFD-5: Nouvel endpoint backend `GET /api/reseau-assistantes` (verbe GET, route en kebab-case `reseau-assistantes`, **un seul paramètre de query string** `scope` de cardinalité enum `ville | tout`). Le paramètre est **obligatoire** ; un appel sans `scope` ou avec une valeur hors enum retourne `400 Bad Request` avec un payload ProblemDetails standard (cf. BR-2). Deux requêtes SQL canoniques **distinctes** sont exécutées selon la valeur de `scope` :

  - **`scope=ville`** — résolution du `CodePostal` côté serveur depuis la session (`SELECT CodePostal FROM Employee WHERE EmployeeId = @SessionEmployeeId` exécuté en pré-requête), puis :
    ```sql
    SELECT [EmployeeId], [Nom], [Prenom], [CodePostal], [Ville], [Telephone]
    FROM [Employee]
    WHERE [CodePostal] = @CodePostal
      AND [Disponible] = 1
      AND [EmployeeId] <> @SessionEmployeeId
    ORDER BY [Nom], [Prenom];
    ```
    avec `@CodePostal` = le code postal résolu en pré-requête, `@SessionEmployeeId` = l'identifiant de l'employée connectée. Si le pré-requête retourne `CodePostal IS NULL` ou chaîne vide pour la session, le backend court-circuite la requête principale et retourne `[]` directement (cf. BR-9).

  - **`scope=tout`** — aucune résolution préalable, requête directe :
    ```sql
    SELECT [EmployeeId], [Nom], [Prenom], [CodePostal], [Ville], [Telephone]
    FROM [Employee]
    WHERE [Disponible] = 1
      AND [EmployeeId] <> @SessionEmployeeId
    ORDER BY [Nom], [Prenom];
    ```

  Règles communes aux deux requêtes :
  - **Tri** : `ORDER BY Nom ASC, Prenom ASC` — ordre alphabétique stable côté serveur ; le frontend n'effectue aucun tri secondaire (cf. BR-8).
  - **Aucun JOIN** (la table est isolée).
  - **Aucun GROUP BY, aucun TOP / LIMIT, aucune pagination** — la liste est retournée intégralement (le volume reste sous le SLA même à l'échelle « tout » — cf. NFC).
  - **Aucune transformation, aucun filtrage applicatif, aucune validation des champs lus** au-delà des trois `WHERE` ci-dessus (`CodePostal`, `Disponible`, `EmployeeId <> session`) — le payload est l'image brute des 6 colonnes sélectionnées (pas de CRUD, cf. BR-12).
  - **Paramétrisation** : `@CodePostal` et `@SessionEmployeeId` sont passés **comme paramètres préparés** (jamais interpolés / concaténés) — anti-injection SQL trivial (cf. BR-3).
  - **`Telephone` retourné brut** : la chaîne est sérialisée telle qu'elle existe en base (format historique FR `06 12 34 56 78` ou `+33 6 12 34 56 78` ou autre — l'admin saisie n'est pas standardisée par cette FEAT) ; aucun formatage applicatif côté backend (cf. BR-10).

- SFD-6: La réponse JSON de l'endpoint backend `GET /api/reseau-assistantes` est de la forme :
  ```json
  [
    {
      "employeeId": 42,
      "prenom": "Fatima",
      "nom": "Cherif",
      "codePostal": "78100",
      "ville": "Saint-Germain-en-Laye",
      "telephone": "06 34 56 78 90"
    },
    {
      "employeeId": 87,
      "prenom": "Claire",
      "nom": "Fontaine",
      "codePostal": "78100",
      "ville": "Saint-Germain-en-Laye",
      "telephone": "06 22 33 44 55"
    }
  ]
  ```
  - Les clés JSON sont **camelCase** (`employeeId`, `prenom`, `nom`, `codePostal`, `ville`, `telephone`) — cf. BR-4.
  - `employeeId` est un entier (sérialisé `Int`, jamais string — symétrique FEAT 17 BR-4).
  - `codePostal` et `ville` peuvent être `null` côté payload si la colonne est `NULL` en base (rare en production mais toléré côté frontend — cf. BR-9 + AC-13) ; les autres champs sont garantis non-null par les contraintes SQL `NOT NULL` (cf. SFD-4).
  - Le payload **n'inclut aucune métadonnée d'enveloppe** (pas de `{ data: [...] }`, pas de `{ items: [...], total: N, scope: "ville" }`) — c'est un tableau JSON à la racine pour rester aligné avec les autres endpoints `GET /api/*` de l'application (cf. FEAT 11 SFD-5, FEAT 15 SFD-8, FEAT 17 SFD-6).

### Barre de recherche — filtre live in-memory

- SFD-10: La barre de recherche est un `<input type="search">` avec placeholder `Rechercher un nom, une ville, un code postal…`, autocomplete désactivé (`autocomplete="off"`), `aria-label="Rechercher"`, à l'intérieur d'un conteneur `.search` contenant aussi (a) une icône loupe SVG positionnée absolue à gauche (18×18, color `var(--nj-ink-400)`, `pointer-events: none`) et (b) un bouton croix `.search__clear` positionné absolu à droite (28×28, background `var(--nj-line)`, color `var(--nj-ink-500)`, border-radius 999 px, `display: none` quand le champ est vide, `display: grid` quand non vide — toggle via classe `.has-val` ajoutée au conteneur parent).
- SFD-11: Le filtre live applique l'algorithme suivant **à chaque event `input`** sur le champ recherche (pas de debounce — le volume ≤ 600 lignes garantit < 16 ms / frame, cf. NFC) :
  1. Récupérer `q = input.value.trim()`.
  2. Normaliser `q` via : `lowercase` puis `String.prototype.normalize("NFD")` puis `replace(/[̀-ͯ]/g, "")` (suppression des diacritiques combinants).
  3. Si `q.length === 0` → afficher toutes les rangées de la collection active (`cacheVille` ou `cacheTout` selon `activeScope`) + masquer `.empty` + masquer le bouton croix (`.search` retire la classe `.has-val`).
  4. Sinon, **tokeniser** `q` par espaces (`q.split(/\s+/)`) — chaque token doit matcher en `substring` pour qu'une ligne soit retenue (logique AND multi-mot, héritage mockup `every(w => t.includes(w))`).
  5. Pour chaque ligne `n` de la collection active :
     - Construire `concat = norm(\`${n.prenom} ${n.nom} ${n.ville ?? ""} ${n.codePostal ?? ""} ${n.telephone}\`)` (champ téléphone **inclus** — l'utilisatrice peut chercher par fragment de numéro ; cf. AC-9). La normalisation `norm()` est la même qu'en étape 2.
     - `match = tokens.every(t => concat.includes(t))`.
     - Si `match === true` → la ligne est retenue ; sinon → exclue.
  6. Re-render la liste avec les rangées retenues. Si `length === 0` → afficher `.empty` (`Aucun résultat. Modifiez votre recherche ou changez de filtre.`) ; sinon → masquer `.empty`.
  7. Afficher le bouton croix (`.search` ajoute la classe `.has-val`).
- SFD-11.bis: **Mémoïsation** des chaînes normalisées : au montage initial de chaque cache (`cacheVille` ou `cacheTout`), le frontend pré-calcule pour chaque ligne `n` un champ dérivé `n._normalized = norm(\`${n.prenom} ${n.nom} ${n.ville ?? ""} ${n.codePostal ?? ""} ${n.telephone}\`)` une seule fois et le stocke dans le state. Le filtre à chaque frappe utilise `n._normalized` directement — économise N appels à `normalize("NFD") + replace + lowercase` par frappe (cf. Quantified Goal < 16 ms / frappe). Le champ `_normalized` n'est **jamais** rendu dans le DOM ; il est strictement interne au state React.

### Segmented toggle « Ma ville » / « Tout » + cache mémoire

- SFD-12: Le segmented toggle est un conteneur `.seg` contenant deux boutons `.seg__btn` :
  - `<button class="seg__btn is-active" data-scope="ville">Ma ville</button>`
  - `<button class="seg__btn" data-scope="tout">Tout</button>`

  La pill **active** porte la classe `.is-active` (background `var(--nj-ink-900)`, color `#fff`, box-shadow `var(--nj-shadow-sm)`) ; la pill **inactive** est `background: transparent; color: var(--nj-ink-500);`. Au montage initial, `Ma ville` est `.is-active` (état par défaut, cf. SFD-7).

- SFD-13: Le comportement au **clic** sur une pill du toggle est le suivant (orchestré par un handler unique `onScopeClick(targetScope)`) :
  1. Si `targetScope === activeScope` → no-op (clic sur la pill déjà active, aucun effet).
  2. Sinon, mettre à jour `activeScope = targetScope`, basculer la classe `.is-active` entre les deux boutons.
  3. **Réinitialiser** `searchQuery = ""` et vider visuellement le champ recherche + masquer le bouton croix (cf. AC-11). Le rationale : un filtre tapé pour le scope précédent n'a pas nécessairement de sens dans le nouveau scope, et l'utilisatrice consulte généralement une vue fraîche après bascule.
  4. **Récupérer la collection cible** :
     - Si `targetScope === "ville"` → la collection est `cacheVille` (toujours non-null après le montage initial — cf. SFD-7) → re-render direct **sans appel réseau**.
     - Si `targetScope === "tout"` ET `cacheTout !== null` → re-render direct **sans appel réseau** (cache déjà peuplé par un clic précédent dans le cycle de vie du composant).
     - Si `targetScope === "tout"` ET `cacheTout === null` → déclencher **un seul** appel `GET /api/reseau-assistantes?scope=tout`, afficher l'état de chargement (cf. SFD-14), au succès stocker le résultat dans `cacheTout` et re-render ; à l'échec afficher l'état d'erreur (cf. SFD-15).
  5. Le re-render applique le filtre courant (`searchQuery` est `""` après l'étape 3, donc affichage de la collection complète).

- SFD-13.bis: **Cycle de vie mémoire** (load-bearing) :
  - **Montage** du composant (`useEffect` `[]` côté React, `onMount` côté Vue, `OnInitializedAsync` côté Blazor) : initialise `cacheVille = null`, `cacheTout = null`, `activeScope = "ville"`, déclenche `GET ?scope=ville`, au succès assigne `cacheVille = response` (pré-mémoïsation `_normalized` cf. SFD-11.bis).
  - **Démontage** du composant (navigation vers une autre route SPA, logout, fermeture onglet) : les références `cacheVille`, `cacheTout`, `searchQuery`, `activeScope`, `error` sont **automatiquement libérées** par le moteur du framework (React unmount, Vue beforeUnmount, Blazor Dispose) — aucun nettoyage explicite via `useEffect cleanup` n'est requis (les références ne fuient pas car aucun closure n'est posé sur `window` / `globalThis` / store global ; cf. BR-13).
  - **Remontage** ultérieur (l'utilisatrice revient sur `/contacts` depuis une autre page) : le cycle complet redémarre — nouveau `GET ?scope=ville`, nouveau `cacheVille`, nouveau `cacheTout = null`. **Aucune** lecture d'un cache persistant (cf. BR-13). Le rationale documenté : sur mobile bas débit, l'utilisatrice tolère un appel réseau de 350 ms à chaque visite ; en revanche, elle ne tolère pas que l'app conserve en mémoire ou en stockage local 80 KB de données entre les visites — l'OS pourrait tuer le process sous pression mémoire (cf. NFC compliance « ne pas consommer la mémoire du téléphone »).

### États de chargement, vide et erreur

- SFD-14: Pendant le chargement (initial `GET ?scope=ville` au montage, OU premier `GET ?scope=tout` déclenché par le toggle), la zone `.list` rend un **squelette** minimal — par exemple 5 placeholders `.row` au layout identique avec background `var(--nj-line-soft)` et hauteur figée 60 px (séparateur préservé). Le champ recherche est rendu désactivé (`disabled`) pendant un chargement. **Le segmented toggle reste cliquable** pendant un chargement secondaire (`scope=tout` après le montage) — un clic « Ma ville » alors que `scope=tout` est en train de charger annule l'opération (`AbortController` côté frontend) et restaure immédiatement la vue cachée `cacheVille` (cf. AC-15).

  **États vides** distincts (libellés non interchangeables) :
  - Si `cacheVille` reçu est `[]` (aucune disponible dans le code postal de la session) ET `activeScope === "ville"` → afficher `<div class="empty show"><b>Aucune assistante maternelle disponible dans votre ville.</b><span>Essayez « Tout ».</span></div>` (cf. AC-12).
  - Si `cacheTout` reçu est `[]` (aucune disponible nulle part) → afficher `<b>Aucune assistante maternelle disponible.</b>` (sans suggestion de toggle puisque les deux scopes sont vides).
  - Si filtre recherche actif produit un résultat vide (collection courante non vide mais aucune ligne ne matche `searchQuery`) → afficher `<b>Aucun résultat.</b><span>Modifiez votre recherche ou changez de filtre.</span>` (cf. AC-10).

- SFD-15: Si l'un des deux GETs échoue (timeout, 5xx, erreur réseau, déconnexion 401), la zone scrollable affiche un message d'erreur générique `<div class="empty show"><b>Impossible de charger la liste.</b><button>Réessayer</button></div>` (style : texte centré `var(--nj-ink-500)`, bouton coral cliquable qui re-déclenche le GET avec le `scope` courant). Aucune information technique (stack trace, code HTTP, message d'erreur SQL) n'est exposée (cf. BR-11, AC-14). **Le cache de l'autre scope, s'il est déjà peuplé, n'est pas invalidé** par l'échec du scope courant — l'utilisatrice peut basculer pour récupérer une vue fonctionnelle (cf. AC-16). Si le 401 est reçu, le client HTTP global redirige vers `/login` (comportement applicatif standard hors scope de cette FEAT).

## Business Rules

- BR-1: l'endpoint `GET /api/reseau-assistantes` est protégé par le même middleware d'authentification que les autres endpoints `/api/*` de l'application (cf. `spec-connexion`) ; une requête sans token JWT valide retourne `401 Unauthorized` ; le frontend redirige alors vers `/login` (comportement standard du client HTTP de l'app).
- BR-2: le paramètre `scope` est **strictement validé** côté serveur — valeurs admises `"ville"` et `"tout"` (case-sensitive lowercase) ; toute autre valeur (`"Ville"`, `"all"`, `"ALL"`, chaîne vide, paramètre absent, paramètre multiple `?scope=ville&scope=tout`) retourne `400 Bad Request` avec un payload ProblemDetails minimal (sans détail technique exposé à l'utilisatrice — cf. BR-11).
- BR-3: la requête SQL est **paramétrée** (`@CodePostal`, `@SessionEmployeeId`) — aucune concaténation de chaîne, aucune interpolation de variables non échappées (cf. `rules/library-and-stack.md §B`, conventions cross-FEAT héritées) ; le `CodePostal` provient **exclusivement** d'une lecture base sur la session côté serveur (cf. SFD-5), jamais d'un input client (le frontend ne passe pas le `CodePostal` en query param — anti-tampering symétrique FEAT 11 BR-3).
- BR-4: les champs JSON renvoyés par le backend sont sérialisés en **camelCase** : `employeeId`, `prenom`, `nom`, `codePostal`, `ville`, `telephone` (cf. `rules/library-and-stack.md §6.bis.3`). Aucune sérialisation en PascalCase ou snake_case.
- BR-5: les rangées sont rendues dans l'ordre du tableau JSON (donc trié par `ORDER BY Nom ASC, Prenom ASC` côté backend) ; le frontend **ne re-trie pas** côté client (le tri est server-state-driven — single source of truth, héritage FEAT 17 BR-8).
- BR-6: l'endpoint **ne retourne JAMAIS** d'employée avec `Disponible = 0` ni avec `Disponible IS NULL` (le filtre est `Disponible = 1` strict côté serveur — cf. SFD-5) ; le frontend n'a aucune logique de re-filtrage sur `disponible` car la propriété n'est pas exposée dans le payload (le champ `Disponible` est lu en SQL mais pas sérialisé dans la réponse JSON — cf. SFD-6).
- BR-7: l'endpoint **exclut systématiquement** la fiche de la session connectée du payload (`WHERE EmployeeId <> @SessionEmployeeId` dans les deux scopes — cf. SFD-5) ; l'utilisatrice ne voit jamais sa propre ligne dans la liste, ni en « Ma ville » ni en « Tout ». Cette règle vise à éviter la confusion (« pourquoi suis-je dans ma propre liste de contacts ? ») et n'a pas de finalité sécurité (la fiche de la session est déjà visible via `/donnees` FEAT 18).
- BR-8: l'endpoint ne pagine pas (cf. SFD-5) — le volume attendu (≤ 600 lignes pour `scope=tout` à l'échelle actuelle) est inférieur au seuil où une pagination apporterait un gain net (au-delà de 1500 lignes, une FEAT future pourrait introduire une pagination cursor-based ; out of scope ici).
- BR-9: si l'employée connectée a un `Employee.CodePostal` NULL ou chaîne vide (cas pathologique compte incomplet), le backend court-circuite la requête principale de `scope=ville` et retourne `[]` immédiatement (cf. SFD-5) avec un log WARN structuré côté backend (`event=missing_postal_code, employee_id=N`) ; le frontend affiche l'état vide `Aucune assistante maternelle disponible dans votre ville. Essayez « Tout ».` (cf. SFD-14) et l'utilisatrice peut basculer sur « Tout » qui fonctionnera normalement.
- BR-10: aucune validation, aucun filtrage, aucune transformation des champs lus côté backend — le payload est l'image brute des 6 colonnes de la table `dbo.Employee`. Le `Telephone` est retourné tel quel (la spec assume que les valeurs en base sont conformes au format historique — pas de re-formatage applicatif côté serveur ni côté frontend). Le frontend l'affiche tel quel en font mono.
- BR-11: aucune information technique (stack trace, exception SQL, nom de colonne brut, code HTTP) n'est exposée dans les messages d'erreur côté frontend ; les libellés sont des labels statiques en français (`Impossible de charger la liste.`, `Aucune assistante maternelle disponible dans votre ville.`, `Aucune assistante maternelle disponible.`, `Aucun résultat.`, `Modifiez votre recherche ou changez de filtre.`) — cohérent avec la stratégie des autres FEATs (cf. FEAT 15 BR-15, FEAT 17 BR-11).
- BR-12: aucune écriture en base n'est déclenchée par cette FEAT — la table `dbo.Employee` est lue uniquement par `GET /api/reseau-assistantes` ; aucun endpoint `POST` / `PUT` / `DELETE` n'est introduit. La mise à jour du champ `Disponible` (l'employée bascule sa disponibilité) relève de FEAT 18 `spec-mes-donnees` (out of scope).
- BR-13: aucun cookie, header de session custom, state local persistant (localStorage, sessionStorage, IndexedDB, cache HTTP côté Service Worker) n'est introduit par cette FEAT — les caches mémoire `cacheVille` et `cacheTout` vivent **strictement** dans le state du composant React / Vue / Blazor et sont libérés au démontage (cf. SFD-13.bis). Le rationale (load-bearing pour la NFC compliance « ne pas consommer la mémoire du téléphone ») : 80 KB conservés entre visites multipliés par N pages persistantes saturent rapidement la mémoire OS sur device bas-de-gamme.
- BR-14: aucun log applicatif côté serveur n'enregistre l'identité de l'employée consultante ni les codes postaux consultés (consultation anonyme — cf. NFC compliance) ; les logs techniques (latence requête, code HTTP, erreur SQL) restent en place mais ne référencent **jamais** `session.EmployeeId` ni `@CodePostal` dans des messages de niveau INFO ou supérieur (DEBUG accepté pour le développement, désactivé en production).
- BR-15: **aucun bouton d'appel téléphonique, aucun bouton SMS, aucun lien `<a href="tel:…">` ou `<a href="sms:…">`** n'est rendu dans la page `/contacts` — le téléphone est strictement **texte affiché** que l'utilisatrice copie ou note, et utilise hors-app via le composer natif iOS / Android. Cette décision intentionnelle (l'application **ne gère pas la communication**) est documentée comme contrainte produit explicite ; un avenant pourra ultérieurement introduire un `<a href="tel:…">` discret si la politique projet change, mais ce n'est pas dans le périmètre de cette FEAT.
- BR-16: la barre de recherche **n'expose aucune requête réseau** par frappe — le filtre est purement in-memory côté frontend (le payload du scope actif a déjà été chargé au mount ou au premier toggle, cf. SFD-7 + SFD-13). Cette décision intentionnelle (pas de search-as-you-type côté serveur) est justifiée par le volume attendu (≤ 600 lignes — cf. NFC) ; au-delà de 5000 lignes, une FEAT future pourrait introduire une recherche serveur (out of scope).
- BR-17: la normalisation du filtre (`lowercase + NFD + strip diacritiques`) est appliquée **identiquement** au texte tapé par l'utilisatrice ET à la concaténation `prenom + nom + ville + codePostal + telephone` de chaque ligne — la mémoïsation `_normalized` côté frontend (cf. SFD-11.bis) pré-calcule la concaténation normalisée une seule fois au chargement du payload pour économiser les opérations à chaque frappe. Match `String.includes` (substring, sans regex, sans wildcard) avec tokenisation par espace en AND multi-mot (`every`).
- BR-18: si le design system actif (shadcn / Vuetify / Radzen) fournit un composant `Input` natif pour le champ recherche ET un composant `Toggle` / `SegmentedControl` natif pour le scope, ils **DOIVENT** être utilisés en priorité avec override de tokens — le CSS isolé du mockup ne complète que pour la fidélité visuelle (cf. `rules/quality.md §B`).
- BR-19: la bascule entre « Ma ville » et « Tout » **ne re-déclenche jamais** un GET si le cache cible est déjà peuplé dans le cycle de vie courant du composant (cf. SFD-13 étape 4) — vérifiable Network DevTools : un cycle « Ma ville » (load) → « Tout » (load) → « Ma ville » (cache hit) → « Tout » (cache hit) → ... émet exactement **deux** requêtes HTTP au total.

## Acceptance Criteria

- AC-1: le menu principal (`spec-menu-principale` FEAT 5) **ne contient plus** d'item « Mes contrats » (ni libellé, ni route cible `/contrats`) — vérifiable par grep statique sur le composant menu (`Grep "Mes contrats|/contrats"` retourne 0 match dans `workspace/output/src/{AppName}/`). À la place, un nouvel item « **Mes Contacts** » est rendu avec une icône SVG cohérente (carnet/people) et une navigation SPA vers `/contacts` au clic. Les autres items (`Mes bébés`, `Rapports`, `Mes données`, `Documentation`, `Se déconnecter`) restent inchangés (héritage FEAT 5 AC-4 + FEAT 17 SFD-1).
- AC-2: la route SPA `/contrats` (sans `/nouveau`) **n'est plus enregistrée** dans le routeur SPA après cette FEAT (si elle l'était dans le code legacy, elle est retirée) ; toute tentative d'accès direct par URL retourne le comportement 404 / fallback du routeur (typiquement redirection vers `/menu` ou rendu d'une page 404 générique). La route `/contrats/nouveau` (FEAT 6 — wizard de création de contrat) **n'est PAS impactée** par cette FEAT et reste enregistrée et fonctionnelle (vérifiable par test E2E : `/contrats/nouveau` ouvre toujours le wizard).
- AC-3: la route `/contacts` est protégée — une utilisatrice non authentifiée est redirigée vers `/login` (héritage FEAT 5 BR-1).
- AC-4: au montage de la page `/contacts`, le frontend envoie **une seule** requête `GET /api/reseau-assistantes?scope=ville` qui retourne un tableau JSON `[ { employeeId, prenom, nom, codePostal, ville, telephone }, ... ]` ; aucune requête additionnelle (telemetry, prefetch `scope=tout`, feature flags) n'est émise (vérifiable Network DevTools — anti N+1).
- AC-5: la requête SQL exécutée par le backend pour `scope=ville` est **strictement** `SELECT [EmployeeId], [Nom], [Prenom], [CodePostal], [Ville], [Telephone] FROM [Employee] WHERE [CodePostal] = @CodePostal AND [Disponible] = 1 AND [EmployeeId] <> @SessionEmployeeId ORDER BY [Nom], [Prenom]`, avec `@CodePostal` résolu en pré-requête depuis la session ; pour `scope=tout` la requête est identique **sans** le `WHERE [CodePostal] = @CodePostal`. Aucun JOIN, aucun GROUP BY, aucun TOP, aucune pagination, aucun tri secondaire (vérifiable par log SQL ou test d'intégration ; cf. AC-21).
- AC-6: le payload est sérialisé en **camelCase** (`employeeId`, `prenom`, `nom`, `codePostal`, `ville`, `telephone`) ; aucune clé en PascalCase ou snake_case ne doit apparaître ; le champ `disponible` **n'est pas** présent dans le payload (lu en SQL pour filtrer, jamais sérialisé — vérifiable par contrat OpenAPI ou test d'intégration JSON).

## Out of Scope

- **modification du champ `Employee.Disponible`** par l'utilisatrice depuis cette FEAT (bascule disponible/indisponible) : cette action relève de FEAT 18 `spec-mes-donnees` (page « Mes Données » qui édite les colonnes du profil) ; cette FEAT 19 lit uniquement la colonne et n'expose aucun toggle, aucun switch, aucune action de mutation.
- **bouton d'appel téléphonique** (`<a href="tel:...">` ou bouton qui invoque `navigator.phone` / iOS WebView phone bridge) : rejeté explicitement par BR-15 — l'application **ne gère pas la communication** ; l'utilisatrice utilise le composer natif iOS / Android hors application. Un avenant pourra introduire `tel:` ultérieurement si la politique projet change.
- **bouton SMS** (`<a href="sms:...">` ou intégration SMS API) : symétrique au point précédent, rejeté.
- **historique des contacts consultés** (tracking par employée connectée des fiches qu'elle a regardées, dernière consultation, recommandations « voir aussi ») : aucun log par employée n'est introduit (cf. BR-14 + NFC compliance) ; consultation anonyme.
- **favoris / pinned contacts** : l'utilisatrice ne peut pas marquer une consœur comme favorite (aucun stockage par employée — cf. BR-12, AC-20) ; FEAT future éventuelle avec une table `EmployeeContact` ou similaire.
- **création / édition / suppression** des lignes de `dbo.Employee` par cette FEAT : la table est lue uniquement ; toute mutation relève de FEAT 3 (inscription), FEAT 18 (Mes données) ou d'une FEAT admin future.
- **recherche serveur** (search-as-you-type avec endpoint dédié, pagination cursor, full-text-search Lucene/Elastic) : non requise vu le volume attendu (≤ 600 lignes — cf. BR-16) ; FEAT future éventuelle si le volume dépasse 5000.
- **filtres avancés** (par âge, par expérience, par langue parlée, par mode de garde — domicile / regroupement) : la liste affiche tous les champs disponibles sans filtre métier au-delà de `Disponible = 1` et du toggle géographique ; un avenant pourra introduire des filtres si la table `Employee` est enrichie.
- **carte géographique** (intégration Google Maps / OpenStreetMap pour visualiser la répartition des contacts sur une carte) : aucune visualisation cartographique ; consultation purement liste-textuelle.
- **tri configurable** par l'utilisatrice (par nom / par distance / par ville) : le tri est fixe `ORDER BY Nom, Prenom` côté serveur (cf. BR-5) ; un avenant pourra introduire un sélecteur de tri si besoin métier émerge.
- **photo de profil** des contacts (avatar à gauche de la rangée) : le rendu canonique exclut explicitement les avatars (`Aucun avatar` — cf. mockup) ; vérifié BR rangée épurée. Un avenant pourra introduire un avatar 36×36 si la maquette évolue.
- **pagination ou virtualisation** (infinite scroll, react-window, intersection observer) : non requise vu le volume (≤ 600 lignes — le navigateur rend la liste complète sans pénalité perceptible) ; FEAT future si volume > 2000.
- **export CSV / vCard** des contacts : aucun bouton d'export ; les contacts ne quittent pas l'application au format fichier.
- **partage social** (boutons « Partager ce contact sur WhatsApp / SMS ») : aucun bouton de partage ; l'utilisatrice copie/transcrit le numéro manuellement si besoin de le transmettre.
- **mode hors-ligne** / cache local persistant : aucun stockage local (cf. BR-13 + AC-20) ; le payload est rechargé à chaque visite de la page (cf. SFD-13.bis).
- **notification push** lors qu'une nouvelle assistante devient disponible dans le code postal : aucune notification ; consultation purement passive à l'initiative de l'utilisatrice.
- **rôles Admin / Parent** : un Admin qui éditerait `Employee.Disponible` ou un Parent qui consulterait l'annuaire des assistantes maternelles disponibles relève d'une FEAT future dédiée avec règles différentes (filtrage par compte parent, scoping par contrat).
