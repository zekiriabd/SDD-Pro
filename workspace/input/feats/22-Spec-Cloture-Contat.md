# Spec: cloture-contrat

FEAT ID: 22-Spec-Cloture-Contat
Spec ID: spec-cloture-contrat
Status: Draft

> **Pré-requis schéma** : ajout d'une colonne `BebeStatut TINYINT NOT NULL DEFAULT 1` à la table existante `dbo.Contrat` (cf. SFD-3 pour le DDL canonique). Domaine de valeurs : `1` = en attente (état initial à la souscription du contrat), `2` = contrat démarré (à terme géré par une FEAT ultérieure), `3` = contrat clôturé/fermé (cette FEAT écrit cette valeur). La colonne n'est **pas** présente dans le schéma `workspace/output/db/schema.json` au moment de la rédaction de cette FEAT — la migration DDL doit être appliquée avant `dev-backend`. Source de vérité = DB existante (cf. `docs/principles/source-first.md`).

## Context

La fiche détaillée bébé `/bebes/{ContratId}` (livrée par FEAT 9 `spec-bebe-detaille`) expose aujourd'hui 3 onglets : **Informations** (identité enfant + parents + contrat + salaire + horaires), **Rapport du jour**, **RDV**. L'assistante maternelle n'a **aucun moyen** depuis cet écran de **clôturer formellement un contrat** quand la relation employé/famille prend fin (préavis, déménagement, scolarisation de l'enfant, rupture conventionnelle). Aujourd'hui, un contrat terminé reste **indéfiniment visible** dans la liste `/bebes` mêlé aux contrats actifs, ce qui pollue le quotidien opérationnel (cards inutiles, statuts trompeurs, compteurs de présents faussés).

Cette spec ajoute un **4ème onglet `Clôture`** à la fiche détaillée bébé, dédié à la fermeture définitive du contrat courant. Le contenu de l'onglet est **strictement statique** (deux blocs de notifications à texte **constant générique** non lié à l'enfant courant — aucune variable, aucun appel backend GET au montage) et expose **un unique bouton d'action FAB** (Floating Action Button rouge, icône croix Material Symbols) qui déclenche une modal de confirmation. À la confirmation, le frontend appelle un nouvel endpoint backend `POST /api/contrats/{ContratId}/cloturer` qui exécute en transaction l'UPDATE `Contrat.BebeStatut = 3` filtré par `ContratId` ET `EmployeeId == session.EmployeeId` (anti-énumération hérité). En cas de succès (`204 No Content`), le frontend affiche un toast de validation puis redirige automatiquement vers `/bebes`.

Le mockup canonique est `workspace/input/ui/22-1-Spec-Cloture-Contat.html`. Il ajoute le bouton tab `<button class="tab" data-tab="cloture">` à la `<nav class="tabs">` existante, une `<section class="pane" data-pane="cloture">` avec deux `<div class="notif">` (warn ambre + info bleu) suivie d'un `<a class="fab">` rouge en bas à droite, ainsi qu'une modal `<div class="confirm">` partagée et un `<div class="toast">` succès. **Trois corrections rédactionnelles** par rapport au mockup brut sont imposées par cette FEAT (cf. SFD-6, SFD-7, SFD-12) : (1) l'icône SVG du tab `<button data-tab="cloture">` est remplacée par un glyphe Material Symbols `cancel` (ou équivalent sémantique de clôture) — le SVG actuel du mockup affiche un check-shield qui n'évoque pas la fermeture ; (2) le bloc info bleu mentionne `Lina n'apparaîtra plus…` — ce libellé est **génériquisé** en `L'enfant n'apparaîtra plus…` car les deux blocs notifications sont des **constantes UI partagées par tous les contrats**, sans interpolation de nom enfant ; (3) la modal de confirmation contient `Clôturer le contrat de Lina ?` — génériquisée en `Clôturer ce contrat ?` (même motif).

L'écran est **autonome** au niveau lecture (rien à fetcher au switch d'onglet — les textes sont littéraux dans le JSX) et **mutateur unique** au niveau écriture (1 POST `/cloturer` au clic confirmer).

## Objective

L'employée connectée ouvre la fiche détaillée d'un bébé `/bebes/{ContratId}`, clique sur le 4ème onglet `Clôture` → le pane affiche instantanément (zero fetch) deux blocs d'information statique générique : (a) un bloc warning `Avant de clôturer, vérifiez auprès des parents` listant 3 éléments constants (documents remis, paiements en suspens, informations à transmettre), (b) un bloc info bleu `Après la clôture` listant 2 conséquences constantes (l'enfant disparaît de la liste `/bebes`, ses données restent consultables dans les Archives — formulation conditionnelle car les Archives sont out of scope de cette FEAT). Au centre-bas du pane, un FAB rouge avec icône croix Material Symbols. Clic sur le FAB → modal de confirmation centrée (icône triangle warning, titre `Clôturer ce contrat ?`, texte explicatif générique, deux boutons `Annuler` et `Oui, clôturer`). Clic sur `Oui, clôturer` → POST `/api/contrats/{ContratId}/cloturer` → backend exécute en transaction `UPDATE dbo.Contrat SET BebeStatut = 3 WHERE ContratId = @ContratId AND EmployeeId = @SessionEmployeeId` avec `EXISTS` anti-énumération → 204 No Content → frontend ferme la modal, affiche un toast vert succès `Contrat clôturé` 2 secondes puis exécute `navigate('/bebes')` (redirection SPA). Le bébé clôturé disparaît automatiquement de la liste `/bebes` au prochain chargement car la requête `GET /api/bebes` (FEAT 11) DOIT être étendue pour filtrer `WHERE c.BebeStatut <> 3` (cf. SFD-15 — effet de bord cross-FEAT obligatoire).

## Quantified Goal (v7.0.0 — anti-GIGO)

- Metric: temps d'affichage de l'onglet Clôture au clic tab (rendu pur, aucun fetch), temps de clôture côté serveur (1 UPDATE 1 ligne par PK `ContratId` avec EXISTS), temps de redirection après confirmation (toast + navigate SPA).
- Target: p95 affichage onglet Clôture < 50 ms côté frontend (rendu JSX littéral, aucune dépendance DOM mesurable), p95 UPDATE `BebeStatut = 3` côté serveur < 80 ms (1 ligne par PK + 1 EXISTS sur même PK), p95 redirection après 204 < 2300 ms (toast 2000 ms + navigate SPA < 100 ms).
- Deadline: livraison stack `fullstack/node-react × ui/shadcn × auth/auth-local` au 2026-09-30.

## Non-Functional Constraints (v7.0.0)

- Expected volume: ~1 clôture / employée / 3 mois (événement rare — fin de contrat de garde) ⇒ < 50 POST `/cloturer` / mois total beta Demo ; aucune lecture supplémentaire (pas de GET dédié à cette FEAT — les textes sont constants frontend).
- Performance SLA: p95 UPDATE < 80 ms (cf. Quantified Goal) ; aucun risque N+1 (1 UPDATE 1 ligne par PK + 1 EXISTS) ; aucun calcul agrégé serveur.
- Data retention: la colonne `BebeStatut` est conservée indéfiniment (pas de purge automatique) ; un contrat à `BebeStatut = 3` reste consultable côté DB (forensic, RGPD, contestation prud'homale) mais n'est **plus rendu** dans `/bebes` ni `/rapports` (cf. SFD-15, SFD-16) ; aucune anonymisation auto (charge utilisateur / DBA si demande RGPD parent).
- Compliance: RGPD — la clôture ne supprime **aucune donnée personnelle** (employeur, contrat, rapports historiques restent en base) ; le changement de statut est une opération **logique** ; un audit log (qui a clôturé quand) n'est **pas** capturé dans cette FEAT (out of scope — pas de colonne `DateCloture` ni `ClotureBy` ; le `BebeStatut` est un TINYINT sans timestamp distinct, assumé acceptable pour beta — une FEAT future pourra ajouter ces colonnes si besoin).
- Integration: 1 nouvel endpoint backend `POST /api/contrats/{ContratId}/cloturer` (zero body, idempotent par construction) ; lecture/écriture de la colonne nouvelle `dbo.Contrat.BebeStatut` ; effet de bord obligatoire sur l'endpoint existant `GET /api/bebes` (FEAT 11 SFD-5 / FEAT 15 SFD-7) — ajout du filtre `WHERE c.BebeStatut <> 3` (cf. SFD-15) ; effet de bord obligatoire sur l'endpoint `GET /api/employee/rapports/aujourdhui` et `/historique` (FEAT 21 SFD-7, SFD-14) — ajout du même filtre `c.BebeStatut <> 3` (cf. SFD-16) ; aucune passerelle externe ; aucune notification SMS / email / push aux parents (out of scope — l'employée gère la communication parents manuellement, cf. blocs notif warn).
- Degraded mode: si l'UPDATE échoue (5xx, timeout, contrainte SQL), le frontend affiche un toast d'erreur générique `Échec de la clôture. Le contrat reste actif.` et **n'effectue pas** la redirection vers `/bebes` (la modal reste fermée, le pane Clôture reste affiché pour permettre une nouvelle tentative) ; si l'employée tente de clôturer deux fois le même contrat (double-clic, retry réseau), le 2ème POST matche 1 ligne (déjà à 3) — l'UPDATE est idempotent par construction (`SET BebeStatut = 3` sur une ligne déjà à 3 est un no-op fonctionnel, aucun trigger / timestamp d'audit) — 204 retourné, frontend re-affiche toast + re-redirige (UX cohérente cf. BR-5) ; si la colonne `BebeStatut` est manquante en base (migration non appliquée), le backend retourne 500 avec log structuré WARN (cas conceptuel — la colonne est un pré-requis dur, pas un fallback silencieux ; sans elle l'endpoint est non-fonctionnel) ; si la session expire (401) avant le POST, le frontend redirige vers `/login` (cf. `spec-connexion`) — la modal est fermée avant redirection ; aucun cache offline.

## Actors

- Employée connectée : assistante maternelle authentifiée, identifiée par son `EmployeeId` issu de la variable singleton de session. Seule autorisée à clôturer un contrat dont `Contrat.EmployeeId == session.EmployeeId`. Aucun accès à l'onglet Clôture sans authentification (toute la fiche `/bebes/{ContratId}` est gardée — héritage FEAT 9).
- Parent (Employeur) : acteur **passif** — n'a aucune interaction directe avec l'application SDD lors de la clôture. La communication des documents/paiements/informations légales (cf. bloc notif warn) est **hors scope SDD** et reste à la charge manuelle de l'employée (face-à-face, courrier, email perso).

## Functional Needs

### Point d'entrée et navigation

- SFD-1: La spec **étend `spec-bebe-detaille` (FEAT 9)** : la fiche `/bebes/{ContratId}` passe de 3 à 4 onglets ; les 3 onglets existants (`Informations`, `Rapport du jour`, `RDV`) sont **inchangés** en terme de route, layout, logique métier, et badges compteur ; seul est ajouté un 4ème bouton tab + une 4ème `<section class="pane">`.
- SFD-2: Aucune nouvelle route SPA n'est introduite (le switch d'onglet est strictement côté client, sans navigation URL — cohérent avec FEAT 9 SFD-9) ; la navigation post-clôture vers `/bebes` (cf. SFD-13) utilise `useNavigate()` / équivalent stack frontend.
- SFD-3: DDL canonique de la migration `BebeStatut` (à appliquer une fois par environnement, idempotent via `IF NOT EXISTS`) :
  ```sql
  IF NOT EXISTS (
    SELECT 1 FROM sys.columns
    WHERE Name = N'BebeStatut'
      AND Object_ID = Object_ID(N'dbo.Contrat')
  )
  BEGIN
    ALTER TABLE dbo.Contrat
      ADD BebeStatut TINYINT NOT NULL CONSTRAINT DF_Contrat_BebeStatut DEFAULT 1;
  END;
  ```
  - La contrainte `DEFAULT 1` initialise toutes les lignes préexistantes à `1` (= en attente — état non bloquant pour les contrats actifs hérités qui ne sont **pas** encore « démarrés » au sens applicatif).
  - Domaine de valeurs **explicite** : `1` = en attente, `2` = contrat démarré (réservé à une FEAT future qui basculera de 1 à 2 lors du premier `RapportJournee` ou autre signal — hors scope ici), `3` = contrat clôturé (écrit par cette FEAT).
  - Aucun CHECK CONSTRAINT n'est ajouté (le domaine est libre côté DB ; la validation valeur ∈ {1,2,3} est faite côté backend service layer pour permettre une extension future sans migration DDL).

### Topbar et tabs

- SFD-4: La topbar de la fiche `/bebes/{ContratId}` (héritage FEAT 9 SFD-6) est **inchangée** : flèche retour, nom complet bébé, avatar circulaire.
- SFD-5: La barre `<nav class="tabs">` (héritage FEAT 9 SFD-8) reçoit un **4ème bouton tab** à droite des 3 existants : `<button class="tab" data-tab="cloture">`. Le rendu suit la convention du mockup (lignes 321-324) : icône SVG 18×18 px + libellé texte `Clôture`. L'icône **N'EST PAS** celle du mockup brut (`<path d="M9 11l3 3L22 4">` — un check-shield qui évoque la validation, pas la clôture) ; elle est remplacée par un **glyphe Material Symbols** sémantique de clôture/fermeture. Options canoniques (le choix exact est laissé à la phase technique, **invariant testable** : le rendu doit visuellement évoquer la fermeture/clôture, pas la validation) :
  - Material Symbols `cancel` (cercle avec croix interne) — recommandé
  - Material Symbols `block` (cercle barré) — alternative
  - Material Symbols `lock` (cadenas fermé) — alternative
  - Material Symbols `close` (croix simple sans cercle) — alternative
- SFD-6: Le clic sur le tab `data-tab="cloture"` active le pane `<section data-pane="cloture">` (classe `is-active` togglée — héritage FEAT 9 SFD-9) et désactive les 3 autres panes ; le scroll vertical du conteneur `.panes` est remis à zéro au switch (héritage FEAT 9). Aucun appel backend n'est déclenché au switch (le pane est statique).

### Onglet 4 — Clôture du contrat

- SFD-7: Au montage initial de la fiche `/bebes/{ContratId}`, le contenu du pane `data-pane="cloture"` est **rendu en mémoire** mais reste invisible (CSS `display: none` géré par l'absence de classe `is-active`) ; aucun appel backend n'est nécessaire pour préparer ce pane (les libellés sont des **constantes littérales** dans le code JSX/Razor/component selon stack). Aucun préfetch.
- SFD-8: Le pane Clôture est composé de **deux blocs de notifications statiques génériques** rendus dans l'ordre de haut en bas (cf. mockup lignes 561-590) :
  - **Bloc 1 — Notification warning ambre** `<div class="notif notif--warn">` :
    - Icône `<span class="notif__ic">` (SVG triangle warning Material Symbols `warning` ou équivalent, 18×18 px)
    - Titre `<span class="notif__title">` : **constante littérale** `Avant de clôturer, vérifiez auprès des parents`
    - Liste `<ul class="notif__list">` de 3 items `<li>`, **libellés constants littéraux** :
      1. `<b>Documents remis</b> — certificat de travail, attestation France Travail, dernière fiche de paie, solde de tout compte.`
      2. `<b>Paiements</b> — dernier salaire, congés payés, indemnité de rupture et régularisation (si applicable).`
      3. `<b>Informations</b> — date de fin de contrat, préavis respecté ou indemnisé, coordonnées des parties.`
  - **Bloc 2 — Notification info bleu** `<div class="notif notif--info">` :
    - Icône `<span class="notif__ic">` (SVG cercle info Material Symbols `info` ou équivalent, 18×18 px)
    - Titre `<span class="notif__title">` : **constante littérale** `Après la clôture`
    - Liste `<ul class="notif__list">` de 2 items `<li>`, **libellés constants littéraux GÉNÉRIQUES** :
      1. `<b>L'enfant n'apparaîtra plus</b> dans la liste des enfants gardés.` *(correction par rapport au mockup brut ligne 587 qui dit `Lina n'apparaîtra plus` — le libellé est génériquisé car constant partagé entre tous les contrats)*
      2. `Toutes ses données restent consultables ultérieurement.` *(formulation conditionnelle volontairement vague : le mockup brut ligne 588 dit `dans les Archives` mais l'écran Archives n'existe pas et est out of scope ; on ne promet donc pas un endroit spécifique, on indique seulement que les données sont conservées)*
- SFD-9: **Aucune variable** n'est interpolée dans les deux blocs notifications — pas de prénom enfant, pas de nom parent, pas de date contrat, pas de période d'essai, pas de salaire. Les blocs sont des **constantes UI partagées par tous les contrats** ; deux clôtures sur deux contrats différents affichent **exactement les mêmes textes** ; aucun appel backend n'est fait pour les peupler. Si un libellé doit évoluer (typo, version FR amélioration), la modification se fait dans un fichier composant frontend unique (ex. `ClotureTab.jsx`) — pas en base.
- SFD-10: Le **bouton d'action unique** est un FAB rouge en bas-droite du pane `<a class="fab" id="cloture-fab" style="background: var(--nj-danger);">` (cf. mockup lignes 594-596). Il porte une icône SVG croix `<line x1="18" y1="6" x2="6" y2="18">` + `<line x1="6" y1="6" x2="18" y2="18">` (la croix simple est correcte pour le FAB — c'est l'icône **tab** SFD-5 qui doit être corrigée, pas le FAB). Aucun libellé texte n'est rendu dans le FAB (icône seule, attribut `aria-label="Clôturer le contrat"` obligatoire pour accessibilité). Le FAB est **toujours actif et cliquable** dans cette FEAT (pas de gating sur `BebeStatut` courant — un re-clic sur un contrat déjà clôturé matche 1 ligne mais reste sémantiquement idempotent, cf. BR-5 ; un état `disabled` du FAB pour contrats déjà `BebeStatut = 3` est out of scope — la liste `/bebes` filtre déjà ces contrats, donc l'employée n'arrive pas sur la fiche d'un contrat clôturé en flow normal).
- SFD-11: Le pane Clôture ne contient **aucun autre élément** : pas de section identité enfant, pas de récap contrat, pas de formulaire, pas de date saisie, pas de zone commentaire libre. Le scope est minimal : 2 blocs notif + 1 FAB. Toute extension (commentaire de clôture, motif, date prévue, signature) est out of scope de cette FEAT et fera l'objet d'une FEAT ultérieure si besoin.

### Modal de confirmation

- SFD-12: Au clic sur le FAB, le frontend ouvre une **modal de confirmation** centrée à l'écran (cf. mockup lignes 602-616) `<div class="confirm" id="confirm-cloture">` avec animation `popIn 0.26s` (héritage CSS du mockup). La modal est composée de :
  - Scrim semi-transparent cliquable (ferme la modal sans clôturer) `<div class="confirm__scrim" data-cancel>`
  - Sheet centrée verticalement `<div class="confirm__sheet" role="dialog" aria-modal="true">` contenant :
    - Icône warning ronde 56×56 px (Material Symbols `warning` ou triangle SVG)
    - Titre `<div class="confirm__title">` : **constante littérale GÉNÉRIQUE** `Clôturer ce contrat ?` *(correction par rapport au mockup brut ligne 609 qui dit `Clôturer le contrat de Lina ?` — la modal est partagée par tous les contrats, le libellé est génériquisé sans interpolation de prénom)*
    - Texte explicatif `<div class="confirm__text">` : **constante littérale GÉNÉRIQUE** `Cette action met fin au contrat. L'enfant n'apparaîtra plus dans la liste des enfants gardés. Cette opération est définitive.` *(remplace le libellé du mockup ligne 610 qui mentionne `Lina sera déplacée dans les Archives` — Archives out of scope, prénom génériquisé)*
    - Deux boutons côte à côte `<div class="confirm__actions">` :
      - `<button class="confirm__btn confirm__btn--ghost" data-cancel>Annuler</button>` (libellé constant)
      - `<button class="confirm__btn confirm__btn--danger" id="confirm-yes">Oui, clôturer</button>` (libellé constant)
- SFD-13: La fermeture de la modal **sans clôturer** s'effectue par : (a) clic sur le bouton `Annuler`, (b) clic sur le scrim semi-transparent, (c) touche `Escape` clavier (accessibilité — héritage cohérence FEAT 21 SFD-21). À la fermeture, **aucun appel backend** n'est envoyé ; le pane Clôture reste affiché avec ses deux blocs notif visibles et son FAB cliquable (l'employée peut re-tenter la clôture plus tard ou changer d'onglet).
- SFD-14: Au clic sur le bouton `Oui, clôturer`, le frontend exécute le **flow de clôture** suivant en séquence stricte :
  1. POST `/api/contrats/{ContratId}/cloturer` (aucun body — le `ContratId` provient du segment URL de la page courante `/bebes/{ContratId}`, l'EmployeeId provient de la session JWT) qui exécute le SQL :
     ```sql
     UPDATE dbo.Contrat
        SET BebeStatut = 3
      WHERE ContratId = @ContratId
        AND EmployeeId = @SessionEmployeeId
        AND EXISTS (
          SELECT 1 FROM dbo.Contrat c2
           WHERE c2.ContratId = @ContratId
             AND c2.EmployeeId = @SessionEmployeeId
        );
     ```
     Note : le filtre `WHERE c.EmployeeId = @SessionEmployeeId` est **techniquement suffisant** à lui seul (le `EXISTS` redondant est conservé pour symétrie défensive avec FEAT 21 SFD-12 — le pattern « `WHERE` + `EXISTS` même prédicat » garantit anti-énumération même si un futur refactoring sépare l'UPDATE en plusieurs étapes). Si `WHERE` matche 0 ligne (contrat hors périmètre OU inexistant), retour `404 Not Found`. Si match 1 ligne, retour `204 No Content` (pas de payload).
  2. À réception du `204`, le frontend ferme la modal (`confirm.classList.remove('is-open')`), affiche un **toast vert succès** `<div class="toast is-show">` (cf. mockup lignes 619-622) avec icône check Material Symbols `check_circle` + libellé **constant** `Contrat clôturé` ; le toast reste visible **2000 ms** (timing recommandé — réglable via constante `TOAST_DURATION_MS`).
  3. Pendant l'affichage du toast (et **pas après** — cf. SFD-15 ordre exact), le frontend déclenche immédiatement la **redirection SPA** vers `/bebes` via `navigate('/bebes')` (ou équivalent du stack frontend). Le toast reste visible côté `/bebes` (rendu hors du conteneur fiche détaillée — pattern de toast global, cf. note d'implémentation BR-9) ; il disparaît automatiquement après 2000 ms cumulés depuis son apparition.
  4. Au montage de `/bebes`, le `GET /api/bebes` est re-déclenché (héritage FEAT 11 / 15) ; le contrat clôturé n'apparaît plus dans la liste grâce au filtre `WHERE c.BebeStatut <> 3` (cf. SFD-15). L'employée constate visuellement la disparition de la card du bébé clôturé.
- SFD-15: **Effet de bord cross-FEAT obligatoire** — l'endpoint `GET /api/bebes` (FEAT 11 SFD-5 / FEAT 15 SFD-6) DOIT être **étendu** par cette FEAT pour filtrer les contrats clôturés : ajout du prédicat `AND c.BebeStatut <> 3` (ou `AND c.BebeStatut IN (1, 2)` selon préférence — sémantiquement équivalent au domaine actuel) à la clause `WHERE` de la requête SQL canonique. Sans ce filtre, un contrat clôturé continue d'apparaître dans la liste `/bebes` ⇒ régression UX majeure. L'agent `dev-backend` qui matérialise cette FEAT 22 DOIT modifier (mode `augment`) le repository / service qui sert `GET /api/bebes` pour ajouter ce prédicat. Le payload JSON retourné par `GET /api/bebes` n'est pas modifié structurellement (pas de nouvelle clé) — seul le contenu (lignes incluses) change.
- SFD-16: **Effet de bord cross-FEAT obligatoire** — symétriquement, les endpoints `GET /api/employee/rapports/aujourdhui` et `GET /api/employee/rapports/historique` (FEAT 21 SFD-7, SFD-14) DOIVENT être étendus par cette FEAT pour filtrer les contrats clôturés : ajout du prédicat `AND c.BebeStatut <> 3` à leurs clauses `WHERE` respectives. Un contrat clôturé ne doit plus apparaître ni dans l'onglet `Rapport du jour` ni dans l'onglet `Historique` de la page `/rapports`. **Décision intentionnelle** : les rapports historiques d'un contrat clôturé **disparaissent** également de l'historique (et pas seulement le rapport du jour) — l'employée ne consulte plus ces rapports via cet écran. Pour la consultation forensic/RGPD post-clôture, une FEAT future `Archives` exposera un endpoint distinct (out of scope). Si cette décision doit être inversée (rapports historiques visibles même post-clôture), le filtre `BebeStatut <> 3` reste sur `aujourdhui` uniquement, et `historique` ne le porte pas — à arbitrer explicitement par le Tech Lead avant `dev-backend`.

### États d'erreur

- SFD-17: Si l'UPDATE échoue avec un code 5xx (timeout DB, contrainte SQL inattendue, panne réseau), le frontend (a) **n'effectue pas** la fermeture de modal automatique — la modal reste affichée avec les deux boutons cliquables, (b) affiche un toast rouge erreur (au lieu du toast vert succès) `<div class="toast is-show toast--error">` avec icône `error` + libellé **constant** `Échec de la clôture. Le contrat reste actif.` qui reste visible 3000 ms, (c) **n'exécute pas** la redirection vers `/bebes` (l'employée peut retenter en re-cliquant sur `Oui, clôturer` — l'UPDATE est idempotent, BR-5).
- SFD-18: Si le POST retourne `404 Not Found` (contrat hors périmètre `EmployeeId`, ou supprimé en parallèle par un autre device), le frontend affiche le même toast erreur générique que SFD-17 — **pas de message distinct 404 vs 5xx** (anti-énumération côté UX : l'employée ne doit pas déduire l'existence/non-appartenance d'un contrat depuis le message d'erreur).
- SFD-19: Si la session JWT a expiré (401 sur le POST), le frontend ferme la modal et redirige vers `/login` (cf. `spec-connexion`) ; aucun toast n'est affiché (la redirection est immédiate). L'employée doit se reconnecter ; la clôture n'est **pas** persistée — elle devra re-tenter manuellement après login (l'opération étant rare, ~1/3 mois, ce coût est acceptable).
- SFD-20: Si le toast succès ne peut pas s'afficher (ex. composant de rendu global non monté — cas conceptuel), le frontend exécute quand même la redirection vers `/bebes` (priorité à la cohérence d'état serveur — le contrat est clôturé en base, l'écran doit refléter cette vérité). Ce cas est conceptuel et ne doit pas se produire en flow normal.

## Business Rules

- BR-1: L'endpoint `POST /api/contrats/{ContratId}/cloturer` vérifie via `EmployeeId = @SessionEmployeeId` dans la clause `WHERE` (et l'`EXISTS` symétrique) que le contrat appartient bien à l'employée connectée AVANT l'UPDATE (cf. SFD-14). Sinon `WHERE` matche 0 ligne, retour 404, **aucune modification** en base — anti-énumération total (jamais 403, toujours 404 sur contrat hors périmètre — symétrique `spec-rapport-du-jour` BR-1 et FEAT 21 BR-3).
- BR-2: La valeur écrite par l'UPDATE est **toujours** la constante littérale `3` côté serveur (constante du SQL). Aucun paramètre `statut` / `value` / `flag` côté query / body / segment URL ne peut être passé pour set une autre valeur (par construction, l'endpoint POST `/cloturer` est sémantiquement orienté « passer à clôturé »). Il n'existe **aucun** endpoint inverse `/reouvrir` ou `/marquer-actif` dans cette FEAT — la réouverture d'un contrat clôturé est out of scope (cas métier rare, à arbitrer si demandé par une FEAT future ; pour la beta, un DBA peut éditer manuellement la valeur en cas de fausse manip).
- BR-3: Les requêtes SQL sont **paramétrées** (`@ContratId`, `@SessionEmployeeId`) ; aucune concaténation de chaîne (anti-injection SQL — symétrique `spec-rapport-du-jour` BR-5, FEAT 21 BR-6).
- BR-4: Aucun audit log (`DateCloture`, `ClotureBy`, `MotifCloture`) n'est capturé côté DB par cette FEAT — la colonne `BebeStatut` est un TINYINT brut sans timestamp ni FK utilisateur attachés. Si un audit est requis à terme, une FEAT future ajoutera les colonnes nécessaires (out of scope explicite — décision documentée pour éviter le surcoût d'une FEAT « audit générique » en beta).
- BR-5: L'UPDATE `SET BebeStatut = 3` est **naturellement idempotent** : un re-POST sur un contrat déjà à `3` matche 1 ligne, set la valeur à `3` (déjà à `3`) → no-op fonctionnel, aucun trigger / colonne `LastUpdated` n'est attaché. Retour 204 dans les deux cas (premier POST et POST suivants). Le frontend re-affiche le toast et re-déclenche la redirection (cf. SFD-14) — comportement assumé cohérent UX, anti-fragile aux double-clics et retries réseau.
- BR-6: La transition d'état `BebeStatut` est **unidirectionnelle** dans cette FEAT : `1 → 3` ou `2 → 3` autorisés (n'importe quel statut courant peut être clôturé) ; `3 → 1` ou `3 → 2` impossibles via endpoint applicatif (cf. BR-2 — pas d'endpoint inverse). La sémantique de `BebeStatut = 2` (contrat démarré) est **réservée** pour une FEAT future et n'est jamais écrite par cette FEAT 22 ni par aucune FEAT existante au moment de la rédaction (donc en pratique seule la transition `1 → 3` se produit en beta).
- BR-7: **Les deux blocs notifications du pane Clôture** (warn + info) sont des **constantes UI partagées** déclarées une seule fois dans le composant frontend ; ils ne contiennent **aucune interpolation de variable contrat** (prénom enfant, nom parent, date, salaire, etc.). Si un libellé est faux ou doit évoluer (typo, version FR améliorée, ajout d'un item à la liste), la modification se fait dans le composant frontend unique — jamais en base ni via un endpoint backend. Aucun fetch backend ne peuple ces blocs (cf. SFD-9).
- BR-8: **La modal de confirmation** (titre + texte explicatif + libellés boutons) est également **constante** sans interpolation de variable contrat (cf. SFD-12). Même contrainte que BR-7.
- BR-9: Le **toast de succès et le toast d'erreur** doivent rester visibles **pendant la redirection SPA** vers `/bebes`. Cela implique que le composant `Toast` (ou équivalent du stack frontend) est rendu **hors du conteneur démonté** par `navigate('/bebes')` — pratiquement, monté au niveau du layout racine `MainLayout` ou via un système de toast global type `react-hot-toast` / `sonner` / mécanisme équivalent stack-specific. L'implémentation exacte est laissée à la phase technique ; **invariant testable** : après confirmation de clôture, le toast est visible **à la fois** dans la dernière frame de `/bebes/{ContratId}` et dans la première frame de `/bebes`, sans clignotement ni démontage prématuré.
- BR-10: L'icône du tab `Clôture` est un **glyphe Material Symbols sémantique de clôture** (cf. SFD-5) — l'icône check-shield du mockup brut est **rejetée**. L'icône du FAB est une **croix simple** (héritage du mockup, ligne 595) — correcte sémantiquement (clôture/fermeture). L'icône de la modal est un **triangle warning** (héritage du mockup, ligne 607) — correcte sémantiquement (action définitive nécessitant confirmation).
- BR-11: Aucune communication automatique aux parents (SMS, email, notification push) n'est déclenchée par cette FEAT. Le bloc notif warn `Avant de clôturer, vérifiez auprès des parents` rappelle à l'employée que la communication des documents légaux et le règlement des paiements en suspens sont à sa **charge manuelle** (face-à-face, courrier, email personnel hors application). Cette décision est volontaire — éviter le couplage avec une passerelle SMS/email et le coût associé en beta.

## Acceptance Criteria

- AC-1: **migration DDL appliquée** : la colonne `dbo.Contrat.BebeStatut TINYINT NOT NULL DEFAULT 1` est présente en base après application de la migration SFD-3 ; toutes les lignes `Contrat` préexistantes ont la valeur `1` (cf. DEFAULT) ; un `SELECT BebeStatut FROM dbo.Contrat WHERE ContratId = {n}` retourne `1` pour tout contrat non encore clôturé par cette FEAT.
- AC-2: **4ème tab rendu** : la fiche `/bebes/{ContratId}` rend désormais 4 boutons `<button class="tab">` dans `<nav class="tabs">` ; le 4ème porte `data-tab="cloture"`, contient un libellé `Clôture` et une icône SVG **non check-shield** (cf. SFD-5, BR-10) ; les 3 onglets précédents (`Informations`, `Rapport du jour`, `RDV`) sont inchangés visuellement et fonctionnellement.
- AC-3: **switch tab Clôture instantané** : clic sur le tab Clôture active le pane `data-pane="cloture"` (classe `is-active`) en < 50 ms ; aucune requête backend n'est envoyée au switch (vérifiable via DevTools Network — 0 fetch déclenché) ; les autres panes sont désactivés (classe `is-active` retirée).
- AC-4: **rendu blocs notif constants** : le pane Clôture affiche exactement 2 `<div class="notif">` dans cet ordre — d'abord `<div class="notif notif--warn">` avec titre `Avant de clôturer, vérifiez auprès des parents` et 3 `<li>` (Documents remis / Paiements / Informations — libellés exacts SFD-8), puis `<div class="notif notif--info">` avec titre `Après la clôture` et 2 `<li>` (libellés exacts SFD-8). Les libellés sont littéraux dans le code source, jamais issus d'un fetch.
- AC-5: **libellés génériques sans nom enfant** : ni le bloc warn, ni le bloc info, ni la modal de confirmation ne contiennent le prénom du bébé courant (`Lina`, `Tom`, `Noé`, etc.) ni aucune variable contrat ; un grep sur le composant `ClotureTab` montre `L'enfant n'apparaîtra plus` (pas `{prenom} n'apparaîtra plus`), `Clôturer ce contrat ?` (pas `Clôturer le contrat de {prenom} ?`), etc. Test programmatique : ouvrir la fiche du bébé A puis du bébé B, capturer le DOM du pane Clôture et de la modal — les textes sont **strictement identiques**.
- AC-6: **FAB rouge présent** : le pane Clôture rend un `<a class="fab">` (ou `<button>` selon implémentation) en position `absolute right:16px bottom:18px` (héritage CSS mockup), fond `var(--nj-danger)` (rouge), icône SVG croix (deux `<line>` formant un X), `aria-label="Clôturer le contrat"`. Le FAB est cliquable (cursor:pointer, pas de `disabled`).
- AC-7: **modal de confirmation au clic FAB** : un clic sur le FAB ouvre la modal `#confirm-cloture` (classe `is-open` togglée) avec animation `popIn` < 300 ms ; la modal contient : icône warning, titre `Clôturer ce contrat ?`, texte explicatif (cf. SFD-12), boutons `Annuler` et `Oui, clôturer`. Aucun POST backend n'est déclenché à l'ouverture de la modal.
- AC-8: **fermeture modal sans clôture** : clic sur `Annuler`, OU clic sur le scrim, OU touche `Escape` ferme la modal (classe `is-open` retirée) **sans envoyer de POST** (vérifiable DevTools Network = 0 fetch sur ces 3 chemins) ; le pane Clôture reste visible avec ses 2 blocs notif et son FAB.
- AC-9: **clôture happy path** : clic sur `Oui, clôturer` déclenche **exactement** un POST `/api/contrats/{ContratId}/cloturer` (zero body, méthode POST stricte — pas PUT ni PATCH) ; le backend exécute l'UPDATE SFD-14 ; le retour est `204 No Content` ; le frontend ferme la modal, affiche un toast vert `<div class="toast is-show">` avec libellé `Contrat clôturé`, et redirige vers `/bebes` via `navigate('/bebes')` (vérifiable par `window.location.pathname === '/bebes'` après ~100 ms).
- AC-10: **persistance DB** : après une clôture happy path (AC-9), un `SELECT BebeStatut FROM dbo.Contrat WHERE ContratId = {n}` retourne `3` (au lieu de `1` ou `2` précédemment). Aucune autre colonne du contrat n'est modifiée (snapshot pre/post UPDATE ne diffère que sur `BebeStatut`).
- AC-11: **contrat disparaît de /bebes** : après une clôture happy path, le rechargement de `/bebes` (déclenché automatiquement par la redirection AC-9, ou manuellement par F5) ne fait **plus apparaître la card du contrat clôturé** ; le compteur de bébés en garde (FEAT 15) reflète ce nouveau total (`N-1` si le contrat clôturé était en garde aujourd'hui).
- AC-12: **rapports masqués pour contrat clôturé** : après clôture, ni l'onglet `Rapport du jour` ni l'onglet `Historique` de `/rapports` (FEAT 21) n'affichent les rapports rattachés au contrat clôturé (vérifiable en consultant `/rapports` avant et après la clôture pour un contrat ayant des `RapportJournee` historiques).
- AC-13: **anti-énumération** : un POST `/api/contrats/{ContratId}/cloturer` avec `ContratId` n'appartenant pas à `session.EmployeeId` retourne 404 (jamais 403) ; aucun UPDATE en base (`WHERE` matche 0 ligne) ; le toast d'erreur frontend est générique (cf. SFD-18) — pas de message distinct vs 5xx.
- AC-14: **anti-tampering valeur** : aucun moyen pour le client de passer une valeur `BebeStatut` autre que `3` via query/body/segment URL ; un POST `/api/contrats/{n}/cloturer?statut=2` ou avec body `{ "statut": 1 }` ignore le paramètre et set `BebeStatut = 3` (constante serveur, BR-2).
- AC-15: **anti-endpoint inverse** : aucun endpoint `/reouvrir`, `/marquer-actif`, `PATCH /api/contrats/{n}` (avec `BebeStatut`) n'est exposé par cette FEAT — un POST sur ces URLs retourne 404 (route inexistante).
- AC-16: **idempotence** : un POST `/cloturer` sur un contrat déjà à `BebeStatut = 3` retourne 204 (UPDATE matche 1 ligne, set à 3, no-op fonctionnel) ; le frontend re-affiche le toast et re-redirige normalement (cf. BR-5) — pas d'erreur 409 Conflict, pas de 200 OK avec body distinct, pas de fail silencieux.
- AC-17: **toast d'erreur sur 5xx/404** : si le backend retourne 500 (DB down, contrainte SQL) ou 404 (contrat hors périmètre), le frontend affiche un toast rouge `Échec de la clôture. Le contrat reste actif.` qui reste visible 3000 ms ; la modal **reste ouverte** ; aucune redirection vers `/bebes` n'est exécutée ; l'employée peut re-cliquer sur `Oui, clôturer` pour retenter.
- AC-18: **session expirée** : si le POST retourne 401 (JWT expiré), le frontend redirige immédiatement vers `/login` ; la modal est fermée avant redirection ; aucun toast n'est affiché.
- AC-19: **icône tab non check-shield** : l'icône SVG du `<button data-tab="cloture">` n'est pas le path `M9 11l3 3L22 4` (check-shield du mockup) ; un grep sur le composant frontend (`ClotureTab` ou composant englobant le `<nav class="tabs">`) ne contient pas cette séquence de coordonnées ; l'icône utilisée est sémantiquement liée à la fermeture (croix, cadenas, cercle barré, cercle avec X — cf. SFD-5).
- AC-20: **mêmes blocs notif pour tous les contrats** : test manuel ou snapshot — capturer le DOM du pane `data-pane="cloture"` sur la fiche du bébé A et du bébé B (deux `ContratId` différents) ; les `innerHTML` des `<div class="notif--warn">` et `<div class="notif--info">` sont strictement identiques caractère pour caractère.

## Dependencies

NONE — cette FEAT est **autonome** au niveau frontend (le pane Clôture n'a aucun pré-requis fetch) et **mutateur isolé** au niveau backend (1 nouvel endpoint, aucune réutilisation de service métier existant à part la connection DB). Les **effets de bord cross-FEAT** documentés SFD-15 et SFD-16 (extension de `GET /api/bebes` et `GET /api/employee/rapports/*`) sont à la charge de l'agent `dev-backend` qui matérialise cette FEAT — il modifie en mode `augment` les repositories existants pour ajouter le prédicat `BebeStatut <> 3`. Pas de dépendance d'ordonnancement avec une autre FEAT en cours (FEAT 21 doit toutefois être déployée avant pour que SFD-16 ait du sens — sinon le filtre est posé sur du code qui n'existe pas encore).

## Out of Scope

- **Réouverture de contrat** (`BebeStatut: 3 → 1`) — pas d'endpoint applicatif ; DBA only pour fausses manips beta.
- **Audit log structuré DB** (`DateCloture`, `ClotureBy`, `MotifCloture`) — colonnes non ajoutées ; le log applicatif INFO (FD-5) suffit en beta.
- **Saisie d'un motif de clôture** côté UI — pas de champ texte dans la modal ; clôture binaire sans contexte.
- **Notification automatique aux parents** (SMS, email, push) — out (cf. BR-11).
- **Génération automatique des documents légaux** (certificat de travail, attestation France Travail) — out ; le bloc notif warn rappelle la charge manuelle.
- **Écran Archives** (`/archives` ou `/bebes/archives`) pour consultation post-clôture — out ; les contrats clôturés restent en DB consultables uniquement via accès direct DBA ou FEAT future dédiée.
- **Disable du FAB pour contrats déjà clôturés** — out (cas conceptuel : la liste `/bebes` filtre déjà ces contrats donc l'employée n'arrive pas en flow normal sur la fiche d'un contrat à `BebeStatut = 3`).
- **Confirmation forte** (saisir le prénom du bébé pour valider, comme GitHub repository deletion) — out ; la modal binaire `Annuler` / `Oui, clôturer` est jugée suffisante pour la beta.
- **Transition `BebeStatut: 1 → 2` (« contrat démarré »)** — out de cette FEAT ; la valeur `2` est documentée dans le domaine SFD-3 pour préparer une FEAT future sans nouvelle migration DDL.
