Définition du système

Qu'est-ce que SDD Pro ?

SDD Pro est un framework de développement logiciel piloté par la spécification (Spec-Driven Development), embarqué dans Claude Code, qui automatise la chaîne complète besoin métier → code production buildé via une orchestration déterministe de 5 agents IA spécialisés.

📋

Le principe

Le PO humain rédige une SPEC fonctionnelle dans un format structuré (Context, Functional Needs, Business Rules, Acceptance Criteria, Functional Deliverables). Cette SPEC est la source de vérité unique. Tout le pipeline en découle.

🤖

La promesse

Une chaîne de 5 agents IA (PO, UI, Arch, Dev-Backend, Dev-Frontend) transforme la SPEC en User Stories, designs UI, code backend et frontend, avec build vert garanti, tests unitaires, coverage et rapport qualité.

🛡️

L'engagement

Anti-derive strict : aucun agent n'invente de besoin, de couleur, de librairie ou de pattern non déclaré. Sur ambiguïté → STOP + ERROR. Pas de devinette, pas de scope creep. Traçabilité 100% SPEC → US → code.

⚡

L'industrialisation

Pipeline idempotent (relancer = comportement identique), parallélisme borné (3 US fullstack par batch), readiness gate déterministe (🟢 GO / 🟡 WARN / 🔴 NO-GO), build loop configurable (default 3, range 1-10), fidelity check text-based v4 + tolérance hex ±5% v5.

Pourquoi SDD Pro

4 garanties différenciantes

Là où les outils LLM classiques génèrent du code "à peu près" qu'il faut auditer ligne à ligne, SDD Pro contractualise la production de code par des règles formelles vérifiables.

🔒

Traçabilité 100%

Chaque SFD, BR, AC, FD de la SPEC est couvert par au moins une User Story (champ Covers). Aucun besoin perdu.

🚫

Zero Derive

Aucune lib hors stack §2.4, aucune couleur hors HTML mockup, aucun pattern non déclaré. STOP + ERROR sur ambiguïté.

🔄

Idempotence

Relancer une commande N fois = état final identique. Aucun état caché. Régénération sûre.

🎯

Build Vert Garanti

Build loop max 3 itérations + readiness gate. Le code livré compile, ou la commande s'arrête avec ERROR actionnable.

Étapes détaillées

Le pipeline pas à pas

Du fichier vide au build vert + tests + coverage, voici les 8 étapes qui composent le cycle complet d'une feature SDD Pro.

  1. Configurer le stack technique (one-shot par projet)

    👤 Tech Lead Phase 0

    Éditer workspace/input/stack/stack.md : activer 1 backend, 1 frontend, 1 design system UI, optionnellement 1 auth et 1+ QA stacks. Renseigner ## Project Config (AppName, BackendName, LibName, DatabaseType, CoverageMin, MaxParallel, QAMode, Capabilities). Définir les variables d'environnement (DB_HOST, DB_USER, DB_PASSWORD, AZ_TENANTID, etc.).

  2. Rédiger la SPEC fonctionnelle

    👤 PO Phase 1 /spec-generate {Nom}

    Mode interactif (max 6 questions) qui produit workspace/input/specs/{n}-{Nom}.md au format strict : Context, Objective, Actors, Functional Needs (SFD-N préfixés), Business Rules (BR-N), Acceptance Criteria (AC-N), Dependencies, Functional Deliverables (FD-N), Out of Scope. Bootstrap aussi workspace/output/context/constitution.md (glossaire, acteurs, stack, ADRs).

    • Les IDs SFD-N, BR-N, AC-N, FD-N sont stables : jamais réordonnés ni renumérotés
    • Pour ajouter : créer SFD-N+1 en fin de liste
    • Pour retirer : supprimer la ligne et régénérer les US

  3. Élicitation structurée (optionnelle, recommandée)

    🤖 Elicitor Phase 1.5 /spec-deepen {n}

    Enrichit la SPEC via 5 techniques d'analyse : Pre-mortem, First Principles, Red Team, Stakeholder Mapping, Inversion. Ajoute 5 sections (Risques, Hypothèses, Edge Cases, Dépendances cachées, Critères de succès) et met à jour constitution.md §7. De facto obligatoire si la SPEC est complexe (score ≥ 2/5).

  4. Découper en User Stories

    🤖 Agent PO Phase 2 /us-generate {n}

    Découpe la SPEC en 1 à 6 User Stories (cible 1-3, warning 4-6, hard cap 6) suivant la règle us-granularity.md (INVEST, regroupement par flux utilisateur, pas par bullet 1:1). Génère workspace/output/us/{n}-{m}-{Name}.md avec User Story, Acceptance Criteria, Covers (traçabilité 100%), Dependencies.

  5. Déposer les mockups HTML statiques

    👤 UX Phase 2.5 Pas d'agent

    Le UX dépose directement workspace/input/ui/{n}-{m}-{Name}.html (HTML statique autonome — libellés exacts, structure DOM, classes CSS, couleurs inline). Aucun agent intermédiaire d'extraction visuelle. dev-frontend lit l'HTML en texte direct et le traduit vers le design system actif (Radzen / Shadcn / Vuetify) via le mapping §2 + §7 du stack UI.

  6. Validation Implementation Readiness Gate

    Script PS · 0 token Phase 2.6 /spec-validate {n}

    v6.0 : 100% déterministe. Validation via PowerShell validate-readiness.ps1 (0 token LLM, 0 agent invoqué) : continuité IDs (SFD/BR/AC/FD), traçabilité Covers, stack actif, Project Config, coïncidence basenames HTML ↔ US, score complexité spec → recommandation /spec-deepen. Produit workspace/output/validation/{n}-readiness.md avec décision 🟢 GO / 🟡 WARN / 🔴 NO-GO. Garde-fou strict ; bypass --force tracé en workspace/output/.audit/force-bypass.log. Review sémantique (AC vagues, ambiguïtés) à la charge du PO humain (agent validator retiré v6.0, économie ~1.4M tokens).

  7. Bootstrap projets + scaffolding DB

    🤖 Agent Arch Phase 3 /arch-init Idempotent

    Phase A : Init Commands §2.2.1 des stacks actifs → projets vides (.csproj / package.json / pyproject.toml) + fichier solution. Phase B (si DatabaseType ≠ none) : introspection READ-ONLY (INFORMATION_SCHEMA), composition connection string en RAM (jamais sur disque), scaffolding Database-First incrémental → workspace/output/db/schema.json + entities. Phase C : CLAUDE.md par projet. Phase D : ADRs sous workspace/output/context/adrs/ADR-{timestamp}-{slug}.md. STEP 12.6 read-back validation v5 : vérifie post-écriture que §4 stack et §6 ADRs index sont cohérents (sinon STOP + ERROR).

  8. Génération du code back+front en parallèle

    🤖 Dev-Backend + Dev-Frontend Phase 4 /dev-run {n}

    Pour chaque US, dispatch parallèle borné (default 3 US par batch = 6 invocations max simultanées) des deux agents Dev. Chacun planifie inline depuis l'US + HTML mockup (frontend = lecture texte directe). STEP 0 HARD-GATE pre-flight v5 : vérifications cheap (Glob seul) avant tout heavy Read pour fail-fast. Build loop configurable v5 via BuildLoopMaxIter (default 3, range 1-10). Fidelity check STEP 11 text-based v4 + tolérance hex ±5% v5 (HexToleranceMaxPct). Skip silencieux si US backend-only ou frontend-only.

    • Plan-then-review optionnel via --plan (checkpoint humain avant code)
    • Bypass NO-GO via --force (déclenche aussi plan-review + audit log v5)
    • Cleanup BREAKING CHANGES post-build (rename → RESOLVED)
    • Lock files atomiques v5 sur LibName partagé (anti race condition)

  9. Tests unitaires + coverage + quality scan

    🤖 Agent QA Phase 5 /qa-generate {n}

    Si QAMode ≠ off|manual, auto-invoqué après build vert. Génère tests unitaires BE+FE selon QA stacks actifs (xUnit, Vitest, bUnit, pytest, JUnit 5, Jasmine). Parsing coverage déterministe (PowerShell parse-coverage.ps1, 0 token) → coverage.json normalisé. Quality scan sonar-like (quality-scan.ps1) → quality.json. Linter / type checker stack-native. Décision finale GREEN / YELLOW / RED non bloquante. Seuil coverage default 80% (WARN si en-dessous).

Modes d'exécution

Manuel ou automatique, au choix

SDD Pro propose deux modes d'exécution complémentaires : un mode manuel granulaire pour le contrôle pas-à-pas et un mode automatique orchestré pour les pipelines de bout en bout.

🛠️ Mode Manuel — Granulaire

Une commande par phase. Le PO/Tech Lead garde le contrôle et peut auditer le livrable de chaque étape avant de passer à la suivante. Idéal pour la première mise en route et pour les features sensibles.

  1. Configurer le stack une fois
    → édition manuelle de workspace/input/stack/stack.md
  2. Créer la SPEC interactivement
    → /spec-generate Auth
  3. Enrichir (optionnel)
    → /spec-deepen 1
  4. Générer les US
    → /us-generate 1
  5. Déposer les mockups HTML dans workspace/input/ui/
    → action manuelle (UX) — plus d'agent UI depuis v4
  6. Valider la readiness
    → /spec-validate 1
  7. Bootstrap projets
    → /arch-init
  8. Planifier (optionnel review)
    → /dev-plan 1
  9. Coder back par US
    → /dev-backend 1-1, 1-2...
  10. Coder front par US
    → /dev-frontend 1-1, 1-2...
  11. Tester + couvrir
    → /qa-generate 1
  12. Diagnostic à tout moment
    → /sdd-status 1

⚡ Mode Automatique — Orchestré

Une seule commande déclenche le pipeline complet (ou une portion). Idéal pour la production en série, les régénérations et les features standard qui suivent un pattern connu. Checkpoints humains préservés sur étapes critiques.

  1. Configurer le stack une fois
    → édition manuelle de workspace/input/stack/stack.md
  2. Créer la SPEC interactivement
    → /spec-generate Auth
  3. Pipeline complet de A à Z
    → /sdd-full 1
    Enchaîne automatiquement :
    • /sdd-run 1 (US + UI)
    • /spec-validate 1 (readiness gate)
    • /dev-plan 1 (si --plan ou WARN)
    • /arch-init
    • /dev-run 1 (back + front parallèle)
    • /qa-generate 1 (auto si QAMode ≠ off)

Variantes orchestrées partielles :

  1. Planification seule (Phases 2-3)
    → /sdd-run 1
  2. Exécution seule (Phases 4-5)
    → /dev-run 1
  3. Forcer malgré WARN/NO-GO
    → /sdd-full 1 --force (déclenche plan-review)
  4. Borner le parallélisme
    → /dev-run 1 --max-parallel 5
💡 Idempotence garantie : les deux modes peuvent être relancés autant de fois que nécessaire. Une re-exécution écrase proprement les artefacts précédents (US, designs, code) sans duplication ni état caché. Le scaffolding DB est incrémental.

Bilan SDD Pro

Pourquoi choisir SDD Pro — et où il faut regarder ailleurs

🏆 Points forts décisifs

  • Code production buildé

    • en 15-30 min pour une feature complète, là où BMAD prend 1-3h et AgentOS exige du code humain.

  • Anti-derive contractuel

    • aucune lib hors §2.4, aucune couleur hors HTML mockup, aucune AC inventée. Le seul framework qui le formalise.

  • Tokens maîtrisés (v5.0 token-lean)

    • Inline Rules + lecture sélective par US + digest CLAUDE.md par projet + scripts déterministes 0-token. Cache hit 97.4% mesuré → coût facturé effectif ~35% de BMAD.

  • Parallélisme borné

    • max 3 US fullstack en parallèle, pour livrer plus vite sans saturer les agents ni perdre en qualité.

  • Idempotence stricte

    • relancer /sdd-full {n} n'altère jamais l'état. Reproductible, auditable.

  • Fidélité visuelle text-based v4 + tolérance hex ±5% v5

    • l'HTML mockup est lu en texte direct ; STEP 11 grep les libellés/composants ; tolérance RGB euclidienne sur les couleurs.

  • HARD-GATE pre-flight v5

    • vérifications cheap (Glob seul) avant tout heavy Read pour fail-fast sur projets mal configurés.

  • Readiness gate déterministe

    • 🟢/🟡/🔴 avant tout code généré : pas de déchet en sortie.

  • Stacks pré-câblés

    • (.NET 10, Node 22, FastAPI, Spring Boot, Kotlin) avec auth Azure AD/Auth0/Keycloak prêts à l'emploi.

  • Constitution + ADRs auto-versionnés

    • avec timestamp atomique anti-collision.

⚠️ Limites à connaître

  • Stacks pré-câblés uniquement

    • : Go, Rust, PHP, Ruby ne sont pas dans le périmètre v5.0.

  • Hard cap 6 US par SPEC

    • pour des features très larges, BMAD scale-adaptive est plus permissif.

  • Pas de phase Brainstorm/Research

    • profonde en amont : BMAD a un agent Analyst et des workflows research.

  • Pas de cérémonial agile

    • (sprint planning, retrospective, sprint-status) — BMAD couvre ces rituels.

  • Tests E2E / perf / accessibilité absents

    • du périmètre — out of scope structurel (cf. accepted-tradeoffs.md). BMAD a un module TEA dédié.

  • Pas de multi-personas en discussion

    • ("Party Mode" BMAD pour faire débattre PM + Architect + Dev).

  • Pas de CI/CD intégré

    • — out of scope défini (BMAD au même niveau).

  • Communauté plus restreinte

    • qu'un BMAD distribué via npm + Discord.

Benchmark vs Superpowers

SDD Pro vs Superpowers — pipeline générateur ou cadre méthodologique ?

🔍 Les 5 différences structurelles à retenir

Au-delà des features, la vraie ligne de partage entre SDD Pro et Superpowers tient en 5 axes fondamentaux.

1. Nature. SDD Pro est un pipeline automatisé (entrée SPEC, sortie code). Superpowers est un cadre comportemental (skills auto-invoqués selon contexte).
Différent
2. Stack. SDD Pro est pré-câblé (.NET, Node, Python, Java, Kotlin). Superpowers est agnostique langage — fonctionne partout.
Superpowers
3. Plateforme. SDD Pro est exclusivement Claude Code. Superpowers est multi-plateformes (6+).
Superpowers
4. Garanties. SDD Pro a des garanties machine (scripts qui rejettent). Superpowers a des garanties textuelles ("Iron Laws" — dépendent de l'obéissance LLM).
SDD Pro
5. Périmètre. SDD Pro génère back+front+DB scaffold. Superpowers ne scaffold pas — il améliore comment l'agent code.
SDD Pro
Bonus — TDD. Superpowers impose TDD strict (skill principal). SDD Pro le rend opt-in (Phase 6).
Superpowers
Bonus — UI. SDD Pro lit le mockup HTML statique en texte direct + fidelity check text-based + tolérance hex ±5%. Superpowers n'a pas de skill UI dédié.
SDD Pro
Bonus — Coût démarrage. Superpowers injecte <2k tokens au boot. SDD Pro charge plus de contexte projet.
Superpowers
💡 Complémentarité plutôt que rivalité : rien n'empêche d'utiliser les deux. SDD Pro orchestre le pipeline SPEC → code sur stacks figés. Superpowers peut se greffer par-dessus pour imposer TDD strict, brainstorming amont et verification systématique aux agents dev-*. Sur un projet Go ou Rust hors périmètre SDD Pro, Superpowers reste pertinent seul. Sur un projet .NET fullstack avec maquettes, SDD Pro reste irremplaçable. Le choix dépend du livrable visé : pipeline d'industrialisation (SDD Pro) vs discipline transverse (Superpowers).
Garanties contractuelles

Ce que SDD Pro garantit (et n'invente jamais)

✅ Garanti par le framework

  • Build vert sur tous les projets actifs (max 3 itérations build loop)
  • Traçabilité 100% SPEC → US → code via champs Covers
  • Idempotence totale : relancer = même résultat
  • Anti-derive strict (libs hors §2.4 → STOP)
  • Isolation par famille (back ne lit pas frontend, et vice-versa)
  • Lecture sélective par US (pas de Glob global)
  • Fidélité visuelle via lecture texte directe du HTML mockup (Frontend) + tolérance hex ±5% v5
  • Readiness gate déterministe avant code (🟢/🟡/🔴)
  • Constitution + ADRs versionnés (workspace/output/context/)
  • Format ERROR 3 lignes (CAUSE / FIX) actionnable

🚫 Hors scope (par design)

  • DevOps / CI / déploiement (out of scope défini)
  • Tests E2E / perf / accessibilité (out of scope, cf. accepted-tradeoffs.md)
  • Génération de doc utilisateur finale
💎 Engagement qualité : le code livré n'est jamais le produit d'une "intuition LLM". Chaque ligne est traçable à une AC d'une US qui couvre un SFD/BR/AC/FD de la SPEC, dans le respect du stack actif déclaré, validé par un build et des tests unitaires. C'est un contrat formel, pas un best-effort.
