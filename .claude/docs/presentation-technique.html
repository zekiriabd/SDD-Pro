Spec-Driven Development pour Claude Code — SPEC fonctionnelle → User Stories → Code (back/front en parallèle)

v6.0.0 4 agents cœur + 2 support ~1800 combinaisons stack 13 commandes 9 règles load-bearing 11 scripts PowerShell

📁 Répertoires .claude/ framework

Tout le cerveau du framework SDD vit ici. Le dossier workspace/ est l'espace projet (entrées humaines + sorties générées) — non documenté ici.

RépertoireRôleContenu clé
.claude/agents/ Définition des 6 agents autonomes (cœur + support). Chaque agent = prompt système + scope strict (reads/writes). po, arch, dev-backend, dev-frontend, qa, elicitor
.claude/commands/ Slash commands invocables par l'utilisateur. Orchestrateurs du pipeline 4 phases. Délèguent aux agents. /spec-generate, /sdd-full, /dev-run, /qa-generate…
.claude/docs/ Documentation chargée à la demande (slim entry CLAUDE.md ~150 lignes). Architecture, workflow, conventions, trade-offs. architecture.md, workflow.md, conventions.md, accepted-tradeoffs.md
.claude/rules/ Règles load-bearing (anti-derive, ownership, granularité, qualité). Inlinées partiellement dans les agents depuis v5.0. 9 règles : responsibilities, file-ownership, qa-coverage, chat-output…
.claude/scripts/ Scripts PowerShell déterministes (0 token LLM). Validation, parsing coverage, scan qualité, smoke tests. validate-readiness.ps1, parse-coverage.ps1, sdd-clear.ps1…
.claude/stacks/ Catalogue des stacks supportés (~1800 combinaisons théoriques). 5 sous-dossiers thématiques. backend/, frontend/, ui/, auth/, qa/
.claude/templates/ Templates Markdown / JSON pour la génération d'artefacts (US, ADRs, rapports QA…). us.template.md, adr.template.md, spec.template.md…
.claude/.metrics/ Baselines de mesure tokens/durée par version (référence économique). baseline-v4.0.0-pvlist.csv

🤖 Agents 4 cœur + 2 support

Tous les agents sont strictement autonomes : aucun ne pose de question utilisateur. Sur ambiguïté → STOP + ERROR (CAUSE / FIX).

🎯 Cœur (4)

AgentPhaseRôleLitÉcrit
po 📋 2 Product Owner — découpe la SPEC en User Stories structurées (cible 1-3, warning 4-6, hard cap 6). Garantit traçabilité 100% (chaque SFD/BR/AC/FD couvert). input/specs/, rules/us-granularity.md, constitution.md output/us/{n}-{m}-*.md, constitution §2-§3 (append-only)
arch 🏗️ 3 Architecte — bootstrap idempotent : projets vides via Init Commands + scaffolding DB READ-ONLY + ADRs majeurs. input/stack/stack.md, stacks/**/*.md (sélectif), DB metadata output/src/{App|Backend|Lib}/ (squelette), output/db/schema.json, ADRs §6
dev-backend ⚙️ 4 Dev Serveur — pour 1 US : lit US + mockup HTML (passif) + stack backend/auth → planifie inline → code services / endpoints / DTOs / mappers + build loop max 3. output/us/{n}-{m}-*.md, input/ui/{n}-{m}-*.html, output/db/schema.json output/src/{BackendName}/** (Edit-augment exclusif)
dev-frontend 🎨 4 Dev Client — pour 1 US : lit US + mockup HTML (source de vérité visuelle) + stack frontend/UI → traduit HTML→composants DS via mapping §2/§7 → code Pages / Components / theme + fidelity check. output/us/{n}-{m}-*.md, input/ui/{n}-{m}-*.html (texte direct), stacks/ui/*.md output/src/{AppName}/** (Edit-augment exclusif)

🛟 Support (2)

AgentPhaseRôleQuand invoqué
elicitor 🔍 1.5 Élicitation structurée — enrichit la SPEC via 5 techniques (Pre-mortem, First Principles, Red Team, Stakeholder Mapping, Inversion). Append 5 sections en fin de SPEC + maj constitution §7 (risques). Optionnel via /spec-deepen {n} · forcé en mode strict /sdd-full
qa ✅ 5 Quality Assurance — génère tests unitaires (back + front), parse coverage (seuil 80%), exécute quality scan sonar-like. Strict scope test : ne modifie JAMAIS le code de prod. Selon QAMode Project Config : off / manual / tests-only / tests+coverage / quality-only / full

⚡ Skills / Commandes 13 commandes

Slash commands invocables. Chaque commande définit son flux STEP par STEP, ses pré-conditions et son output. La plupart sont idempotentes.

CommandePhaseDescription
/spec-generate [Nom] 1 Cadrage interactif d'une SPEC fonctionnelle (3-6 questions). Bootstrap aussi constitution.md au premier appel projet (§1 Identité, §2 Glossaire vide, §3 Acteurs).
/spec-deepen {n} [--quick] 1.5 Élicitation structurée via agent elicitor : 5 techniques (Pre-mortem, First Principles, Red Team, Stakeholder Mapping, Inversion). Mode interactif ou one-shot.
/us-generate {n} 2 Découpe la SPEC en User Stories via agent po. Cible 1-3 US, hard cap 6. Traçabilité 100% obligatoire.
/spec-validate {n} [--json] 2.6 Implementation Readiness Gate 100% déterministe (script PowerShell, 0 LLM). Décision GO / WARN / NO-GO. Sortie output/validation/{n}-readiness.md.
/arch-init 3 Bootstrap solution + projets vides via Init Commands + scaffolding DB READ-ONLY + ADRs majeurs. Idempotent (skip si déjà init).
/dev-plan {n} 3.5 Mode Plan Only : produit les plans techniques output/plans/*.{back|front}.md SANS coder. Permet review humaine avant exécution.
/dev-backend {n}-{m}[:plan] 4 Code serveur d'1 US. Suffixe :plan = Plan Only (pas d'écriture code). Build loop max 3 itérations.
/dev-frontend {n}-{m}[:plan] 4 Code client d'1 US. Lit le mockup HTML directement (texte). Suffixe :plan = Plan Only. Fidelity check textuel obligatoire.
/dev-run {n} [--force] [--max-parallel N] 3 → 4 Orchestrateur dev : arch+db (séquentiel) → back + front en parallèle borné (default MaxParallel: 3 US, range 1-12).
/sdd-full {n} [--plan] [--force] 2 → 5 Pipeline complet de A à Z pour 1 SPEC : us-generate → spec-validate → arch-init → dev-run → qa-generate. Flags : --no-plan-on-warn, --no-validate.
/qa-generate {n} [--mode M] 5 Génère tests unitaires + parse coverage + quality scan via agent qa. Modes : off / quality-only / tests-only / tests+coverage / full / manual.
/sdd-status [{n}] diag Diagnostic du pipeline SDD (lecture seule). Affiche état SPEC / US / build / QA pour 1 SPEC ou toutes.
/sdd-clear [{n}] [--force] [--all] [--quiet] maint Nettoyage des artefacts générés sous workspace/output/. Dry-run par défaut, --force requis pour exécuter.

📜 Rules 9 règles load-bearing

Les règles définissent les invariants opérationnels du framework. Certaines sont inlinées dans les agents (substance v5.0), d'autres sont chargées on-demand.

RègleDescriptionConsommateurs
responsibilities.md Périmètre Allowed / Forbidden de chaque acteur (PO humain, UX Designer, Tech Lead, agents PO/Arch/Dev/QA). Aucun chevauchement. Tous les agents
us-granularity.md Contrat de découpage SPEC → US. Cible 1-3, warning 4-6, hard cap 6. Anti-patterns interdits (1:1 SFD→US, US technique, US par couche…). Agent po
constitution.md Source de vérité partagée (glossaire, acteurs, stack, ADRs). Append-only par section, jamais réécrite intégralement. ADRs en numérotation atomique par timestamp. /spec-generate, po, arch, elicitor
file-ownership.md Matrice ownership des fichiers partagés. Évite les race conditions sur runs parallèles /dev-run. Lock files pour {LibName}/. Tous les agents (inlinée §1-§2 dans dev-*)
stack-completeness.md Anti-derive sur les libs : toute lib utilisée doit figurer en §2.4 du stack actif. §2.4.a CORE (auto-install) vs §2.4.b ON-DEMAND (trigger US). STOP + ERROR si absente. dev-backend, dev-frontend, qa
library-policy.md Politique CVE / origine / version pinnée. Registry canonique uniquement (NuGet, npm, PyPI…). Pas de pre-release sans justification. Vérif CVE post-install. arch (on-demand)
qa-ownership.md Agent QA = seul propriétaire des fichiers de test (patterns *.Tests/, *.spec.ts, __tests__/…). Réciproquement, QA est read-only sur le code prod. Agent qa + dev-* (lecture passive scan forbidden)
qa-coverage.md Seuil 80% (configurable). Schéma coverage.json normalisé cross-stack (coverlet, c8, pytest-cov, JaCoCo, istanbul). Décision YELLOW si gap, RED si test failed. Agent qa
chat-output.md Verbosité minimale du chat : succès = 1L, warning = 1L, erreur = 2L max. Détail dans fichiers output/.... Pas de récap multi-section. Toutes commandes + agents

📄 Fichiers .claude/scripts/

Scripts PowerShell déterministes (0 token LLM). Exécutables hors Claude Code pour audit/maintenance.

ScriptDescription
validate-readiness.ps1Implementation Readiness Gate (Phase 2.6). Vérifie SPEC + US + stack + ACs + traçabilité + IDs stables. Sortie GO / WARN / NO-GO. Remplace agent validator retiré v6.0.
parse-coverage.ps1Parse les outputs de coverage tools (cobertura XML, lcov, JSON) et normalise vers schéma coverage.json (cf. qa-coverage.md §2). Cross-stack.
quality-scan.ps1Quality scan sonar-like cross-stack. Métriques : LoC, complexité, duplications, smells. Sortie quality.json.
sdd-clear.ps1Backend de /sdd-clear. Supprime artefacts workspace/output/. Dry-run par défaut, -Force requis.
framework-smoke.ps1Smoke test cohérence interne du framework. Vérifie que tous les fichiers référencés (rules, templates, stacks) existent et sont parseables.
validate-inline-rules.ps1Détecte le drift Inline Rules : compare la substance inlinée dans agents/dev-*.md avec les fichiers rules/*.md source de vérité.
validate-fidelity.ps1Fidelity check texte-based : grep des libellés/composants extraits du HTML mockup dans le code généré (Phase 4 STEP 11 dev-frontend).
measure-batch.ps1Agrège les tokens consommés par session (lecture .metrics/ + transcripts). Suivi économique des runs.
acquire-libname-lock.ps1Acquiert lock file atomique sur {LibName}/.locks/{Entity}.lock avant écriture parallèle. Anti-race dev-backend / dev-frontend (cf. file-ownership.md §4).
detect-capabilities.ps1Scanne les US d'une SPEC pour détecter les trigger keywords (excel, pdf, redis-cache, cqrs…) et déduit les libs §2.4.b à installer.
mark-breaking-resolved.ps1Marque les sections BREAKING CHANGES du CLAUDE.md projet comme RESOLVED post-build vert (cf. file-ownership.md §6.bis).
